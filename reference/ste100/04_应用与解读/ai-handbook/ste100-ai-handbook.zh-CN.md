# 第 1 篇：基础篇——为什么 STE 能让 AI 输出更有价值

## 1.1 什么是 ASD-STE100

ASD-STE100（Simplified Technical English，简化技术英语）是由欧洲航空航天和国防工业协会（ASD）制定的一套受控语言规范。它最初的目的是确保航空维修文档的清晰性和准确性，避免因语言歧义导致的安全事故。

**核心规则包括：**

| 规则类别 | 核心要求 |
|---------|---------|
| 词汇限制 | 使用约 1800 个批准词汇，每个词通常只有一个含义 |
| 句子结构 | 句子长度不超过 20 个单词，使用简单句 |
| 语态要求 | 优先使用主动语态，避免被动语态 |
| 名词堆叠 | 禁止 3 个以上名词堆叠（如 "system power supply unit" 需改写） |
| 指令清晰 | 操作步骤使用祈使句，动作明确 |
| 避免歧义 | 禁止使用代词 "it" 指代不明，避免隐喻和习语 |

> **注：** 本手册讨论的是 STE 的"思想"而非严格的词汇表。在中文语境下，我们借鉴其核心原则：短句子、主动语态、一词一义、结构清晰、信息密度高。

## 1.2 Karpathy 为什么推荐用它

Andrej Karpathy（前特斯拉 AI 总监、OpenAI 创始成员）在多次演讲和推文中提到，他使用 Simplified Technical English 的原则来约束 LLM 输出。

**核心观点摘录：**

1. **"LLM 输出的最大问题不是信息量不够，而是信息密度太低。"**
   - 普通输出充斥着套话、连接词、冗余修饰
   - STE 风格强制每句话都承载信息

2. **"把 LLM 当成一个有点啰嗦的初级员工，你需要给它明确的写作规范。"**
   - 不加约束的 LLM 倾向于"凑字数"
   - STE 规则相当于给 LLM 一份写作质量标准

3. **"技术文档的理想状态是：每句话都可以被执行或验证。"**
   - STE 风格的文档可执行性强
   - 读者能快速找到所需信息，不需要"阅读理解"

4. **"我让所有 AI 助手都用 STE 风格回答，效率提升了不止一倍。"**
   - 阅读速度更快
   - 误解率更低
   - 信息提取更容易

## 1.3 STE 提升 AI 输出质量的 5 个原理

### 原理 1：降低认知负荷

普通 AI 输出：长段落、复杂句、多层嵌套，读者需要反复阅读才能理解。
STE 输出：短句子、每句一个核心信息、结构分明，读者可以"扫描式阅读"。

**认知科学依据：** 人脑工作记忆容量有限（约 4±1 个信息块），长句会快速耗尽工作记忆。

### 原理 2：减少歧义

普通 AI 输出：大量使用代词、模糊修饰、抽象名词。
STE 输出：明确的名词、具体的动作、可验证的描述。

**AI 场景价值：** 当你把 AI 输出再喂给另一个 AI（Agent 链式调用）时，歧义会被指数级放大。STE 风格是 Agent 之间可靠通信的基础。

### 原理 3：提高信息密度

普通 AI 输出：通常 30%-50% 是"连接词、过渡语、客套话"。
STE 输出：每句话都有实质内容，信息密度可达 80% 以上。

**量化对比：** 同样内容，STE 风格通常能节省 40%-60% 的字数。

### 原理 4：便于结构化提取

普通 AI 输出：格式松散，难以用程序提取关键信息。
STE 输出：结构规整，容易转换为表格、JSON、知识图谱等结构化格式。

**AI 场景价值：** STE 格式的输出更容易被 RAG 系统正确索引和检索。

### 原理 5：建立质量基线

普通 AI 输出：质量波动大，取决于模型心情和提示词技巧。
STE 输出：有明确的规则可以检查和评分，输出质量更稳定。

**AI 场景价值：** 可以用自动化工具检查 STE 合规度，作为输出质量的"守门员"。

## 1.4 STE vs 普通写作：对比示例

### 示例 1：概念解释

| 普通写法 | STE 写法 |
|---------|---------|
| 机器学习是一种人工智能的应用，它使得系统能够从经验中学习和改进，而无需进行明确的编程。机器学习的过程涉及使用数据来训练模型，通过算法来分析数据并从中学习，然后根据学习到的模式做出预测或决策。 | 机器学习是一种 AI 技术。<br><br>它让计算机从数据中学习，不需要人工编写所有规则。<br><br>工作流程：<br>1. 输入训练数据<br>2. 算法分析数据中的模式<br>3. 生成模型<br>4. 模型对新数据做出预测 |

**改进点：**
- 把 2 个长句拆成 4 个短句 + 列表
- 每句只说一件事
- 用编号列表展示流程，一目了然
- 删除"涉及""从而"等连接词

### 示例 2：操作指南

| 普通写法 | STE 写法 |
|---------|---------|
| 在进行系统配置之前，你需要确保已经备份了所有重要的数据，以防止在配置过程中可能出现的意外情况导致数据丢失。同时，建议你关闭所有正在运行的应用程序，这样可以避免配置过程中出现冲突。 | 操作前检查：<br>1. 备份所有重要数据<br>2. 关闭所有运行中的应用程序<br><br>原因：防止数据丢失和程序冲突。 |

**改进点：**
- 使用祈使句直接给出指令
- 把"原因"和"操作"分开
- 删除"在...之前""以防止""建议你"等套话

### 示例 3：邮件沟通

| 普通写法 | STE 写法 |
|---------|---------|
| 非常感谢您抽出宝贵的时间来阅读这封邮件。我是XX公司的张三，我们公司主要提供企业级的 AI 解决方案。我想和您约个时间讨论一下可能的合作机会，不知道您下周是否方便？如果方便的话，请告诉我您的时间安排。 | 主题：约访 - AI 解决方案合作<br><br>您好，<br><br>我是 XX 公司张三。我们提供企业级 AI 解决方案。<br><br>想和您约 30 分钟会议，讨论合作可能。<br><br>您下周哪个时间段方便？<br><br>谢谢。 |

**改进点：**
- 删除客套话，直接进入主题
- 每段一个核心信息
- 明确说明会议时长（30 分钟）
- 问题直接、具体

## 1.5 STE "浓度"概念

STE 不是非黑即白的。根据场景不同，你可以调节 STE 的"浓度"。

### 100% STE：严格模式

**适用场景：**
- 操作手册、维修指南（安全相关）
- Agent 之间的消息传递
- 技术规范、API 文档
- 知识库中的操作指南页

**特点：**
- 每句不超过 20 字（中文约 15-20 字）
- 全部使用主动语态
- 没有形容词和副词
- 每个术语只有一个含义
- 严格的编号和层级

### 80% STE：标准模式（推荐日常使用）

**适用场景：**
- 日常 AI 对话
- 技术文档、README
- 知识卡片、笔记整理
- 工作邮件、即时消息

**特点：**
- 大多数句子简短（90% 在 25 字以内）
- 偶尔使用被动语态（不超过 10%）
- 少量必要的形容词
- 结构清晰，有明确的层级
- 保留少量连接词以保持流畅

### 50% STE：轻度模式

**适用场景：**
- 文章、博客、科普内容
- 产品介绍、营销文案
- 会议纪要、 Brainstorm 记录
- 面向非技术读者的解释

**特点：**
- 段落不超过 4 行
- 关键信息用短句和列表
- 解释性内容可以适当展开
- 保留一定的文学性和可读性
- 核心概念和操作步骤用 STE 风格

**浓度选择指南：**

| 场景 | 推荐浓度 | 原因 |
|-----|---------|------|
| Agent 系统提示词 | 100% | 精确无歧义 |
| 技术操作指南 | 100% / 80% | 可执行、可验证 |
| 知识库页面 | 80% | 信息密度高 |
| 日常 AI 问答 | 80% | 效率与可读性平衡 |
| 邮件/消息 | 80% / 50% | 专业且不失礼貌 |
| 文章/报告 | 50% | 兼顾可读性和信息密度 |
| 创意写作 | 0-50% | 不适用严格 STE |

# 第 2 篇：Prompt 篇——写出 STE 风格的提示词

## 2.1 核心 Prompt 模板

### 基础模板（80% 浓度）

```
请用 Simplified Technical English (STE) 风格回答我的问题。

要求：
1. 使用短句，每句不超过 25 个汉字
2. 每段不超过 3 句话
3. 优先使用主动语态
4. 用编号列表展示步骤或要点
5. 避免使用形容词和副词
6. 删除客套话和连接词
7. 每个术语保持一致

我的问题是：
{在此处输入你的问题}
```

### 可调浓度模板

```
请用 STE（简化技术英语）风格回答。

STE 浓度：{100% / 80% / 50%}

浓度说明：
- 100%：严格模式。每句≤15字，全主动语态，无修饰词，纯信息
- 80%：标准模式。大多数句子简短，偶尔使用被动语态，结构清晰
- 50%：轻度模式。关键信息用 STE 风格，解释性内容可适当展开

输出格式要求：
- 使用 Markdown 格式
- 关键步骤用编号列表
- 概念用加粗标注
- 对比用表格

我的问题：
{在此处输入你的问题}
```

### 超浓缩模式（适合快速获取信息）

```
请用最精简的 STE 风格回答。
要求：
- 只给要点，不给解释
- 用短语，不用完整句子
- 最多 5 条
- 每条不超过 10 个字

问题：{问题}
```

## 2.2 12 个即用 Prompt 模板

### 模板 1：概念解释

**适用场景：** 学习新概念、向他人解释技术术语

```
请用 STE 风格解释【{概念名称}】。

要求：
1. 第一句给出定义（是什么）
2. 用 3-5 个要点说明核心特征
3. 给出 1 个简单的例子
4. 说明它和【{相关概念}】的区别（如果有）
5. 用 80% STE 浓度

输出结构：
- 定义：...
- 核心特征：
  1. ...
  2. ...
- 例子：...
- 与 {相关概念} 的区别：...
```

**效果示例（解释"向量数据库"）：**

> **定义：** 向量数据库是一种存储向量数据的数据库。
>
> **核心特征：**
> 1. 数据以向量形式存储（一串数字）
> 2. 支持相似度搜索
> 3. 速度比传统数据库快
> 4. 常用于 AI 应用
>
> **例子：** 你输入"猫的图片"，系统找到相似的图片。
>
> **与传统数据库的区别：** 传统数据库精确匹配，向量数据库相似匹配。

### 模板 2：技术教程/操作指南

**适用场景：** 让 AI 生成可执行的操作步骤

6. 每步不超过 20 字

- 适用版本：{软件/系统版本}
- 前提条件：
  1. ...
  2. ...
- 操作步骤：
  1. ...
  2. ...
  3. ...
- 验证方法：...
```

## 2.3 Prompt 使用技巧

### 技巧 1：在系统提示词中设置默认 STE 风格

如果你使用支持自定义系统提示词的 AI 工具（如 ChatGPT 自定义指令、Claude 系统提示等），可以把 STE 要求放入系统提示词，这样每次对话都默认使用 STE 风格。

**系统提示词示例：**
```
你是一个专业的技术助手。请始终用 STE（简化技术英语）风格回答。

默认设置：
- 浓度：80%
- 每句不超过 25 字
- 每段不超过 3 句
- 用列表展示要点
- 删除客套话

如果用户要求更详细或更简洁，可以调整浓度。
```

### 技巧 2：用"浓度滑块"动态调节

在对话中可以随时调整浓度：
- "请用更精简的方式说" → 提高浓度
- "请展开解释一下" → 降低浓度
- "请用严格 STE 格式" → 切换到 100%

### 技巧 3：批量处理时使用统一模板

如果你需要处理大量内容（如整理知识库），先设计好固定模板，然后批量调用。这样输出格式一致，便于后续检索和使用。

### 技巧 4：让 AI 自我检查

在 Prompt 最后加上：
```
回答完成后，请用 STE 规则自检，并在末尾给出 STE 合规评分（1-10 分）。
如果评分低于 8 分，请重新改写。
```

# 第 3 篇：知识库篇——用 STE 构建高质量个人知识库

## 3.1 为什么知识库需要 STE 规范

### 问题：知识库为什么会"用不起来"

很多人的知识库面临同样的困境：
- 笔记越积越多，但找不到需要的内容
- 同一件事有多条记录，说法不一致
- 当时记的笔记，回头看不懂
- 想用 AI 检索（RAG），效果很差

**核心原因：** 笔记质量没有标准，信息密度低，结构混乱。

### STE 对知识库的 5 个价值

| 价值 | 说明 |
|-----|------|
| 可读性 | 任何时候打开都能快速理解 |
| 一致性 | 相同概念用相同表述，不混乱 |
| 可检索 | 结构清晰，关键词明确，AI 容易命中 |
| 可复用 | 知识卡片可以直接迁移到其他场景 |
| 可积累 | 质量有基线，越积累越有价值 |

### 一个反例和正例

**普通笔记（差）：**
> 今天学了一下 RAG，感觉挺重要的。就是检索增强生成吧，好像是把知识库和大模型结合起来，让模型能用到自己的数据。大概流程是先把文档切块，然后转向量，存到向量数据库里，用户提问的时候先搜相关的块，然后把搜索结果和问题一起给模型，模型就能根据知识库回答了。好像有很多细节，比如切块的大小、embedding 模型的选择、重排序什么的。

**STE 风格笔记（好）：**
> # RAG（检索增强生成）
>
> ## 定义
> RAG = Retrieval-Augmented Generation
> 让大模型使用外部知识库回答问题的技术。
>
> ## 核心流程
> 1. 文档切块（Chunking）
> 2. 块转向量（Embedding）
> 3. 向量存入向量数据库
> 4. 用户提问 → 转为向量
> 5. 向量数据库中搜索相似块
> 6. 将问题 + 相关块拼接为 Prompt
> 7. 大模型生成回答
>
> ## 关键参数
> - 块大小：通常 500-1000 token
> - 重叠量：通常 10%-20%
> - 召回数量：通常 3-10 块
>
> ## 优化方向
> 1. 更好的切块策略
> 2. 更高质量的 Embedding 模型
> 3. 加入重排序（Rerank）
> 4. 多轮查询改写

## 3.2 STE-Wiki 三层架构设计

### 整体架构

```
┌─────────────────────────────────────┐
│           第三层：产出层              │
│  文章 / 报告 / 方案 / 课程 / 书籍     │
│  （面向输出，50% STE 浓度）          │
├─────────────────────────────────────┤
│           第二层：知识层              │
│  概念页 / 实体页 / 对比页 / 指南页    │
│  （面向理解，80% STE 浓度）          │
├─────────────────────────────────────┤
│           第一层：原子层              │
│  知识卡片 / 术语定义 / 金句 / 数据    │
│  （面向存储，100% STE 浓度）         │
└─────────────────────────────────────┘
```

### 第一层：原子层（100% STE）

**定位：** 知识库的最小单元，像乐高积木一样可以被复用。

**内容类型：**
- 术语定义卡
- 金句/观点卡
- 数据/事实卡
- 方法步骤卡

**特点：**
- 每张卡片只讲一件事
- 严格 STE 格式
- 有明确的标签和关联
- 可以被上层页面引用

**卡片模板：**
```
---
类型: 术语卡 / 观点卡 / 方法卡 / 数据卡
创建日期: YYYY-MM-DD
来源: {出处}
标签: [标签1, 标签2]
---

# {卡片标题}

## 核心内容
{一句话说清楚}

## 详细说明
{3-5 个要点}

## 相关
- [[相关卡片1]]
- [[相关卡片2]]
```

### 第二层：知识层（80% STE）

**定位：** 把原子卡片组织成结构化的知识页面。

**页面类型：**

| 页面类型 | 用途 | 结构 |
|---------|------|------|
| 概念页 | 解释一个概念/技术/理论 | 定义、原理、分类、应用、优缺点 |
| 实体页 | 描述一个具体事物（工具/人物/公司） | 基本信息、核心特征、使用场景、评价 |
| 操作指南页 | 一步步教你做某事 | 前提、步骤、验证、常见问题 |
| 对比分析页 | 比较多个选项 | 维度对比表、选择建议 |

### 第三层：产出层（50% STE）

**定位：** 面向外部输出的成品。

**内容类型：**
- 技术文章
- 项目方案
- 培训课程
- 书籍/电子书
- 分享演讲

**特点：**
- 从知识层组装而来
- 加入叙事逻辑和过渡
- 可以适当降低 STE 浓度以提升可读性
- 完成后反向沉淀为知识卡片

## 3.4 三大工作流

### 工作流 1：摄入（Ingest）——把外部信息变成 STE 笔记

**适用场景：** 读书、看文章、听课程、参加会议

**步骤：**
1. **收集原始素材**
   - 保存原文/录音/截图
   - 标注来源和时间
2. **快速提取要点**
   - 用 AI 生成 STE 风格摘要（使用第 2 篇的摘要模板）
   - 提取 3-7 个核心概念
3. **创建原子卡片**
   - 每个核心概念创建一张知识卡片
   - 使用 100% STE 格式
   - 添加标签和关联
4. **归类到知识层**
   - 检查是否已有相关概念页
   - 有则补充，无则新建
5. **标记待整理**
   - 快速摄入的内容标记 #待整理
   - 定期（如每周）回顾和完善

**AI 辅助 Prompt：**
```
请阅读以下内容，帮我提取成 STE 风格的知识卡片。

要求：
1. 提取 3-7 个核心概念
2. 每个概念生成一张卡片
3. 卡片格式使用标准模板
4. 用 100% STE 浓度
5. 只保留核心信息，删除案例和故事

内容：
{原文}
```

### 工作流 2：查询（Query）——快速找到需要的知识

**适用场景：** 写东西需要资料、遇到问题找答案、复习回顾

**步骤：**
1. **明确查询目标**
   - 你要找的是概念？工具？操作步骤？
2. **使用关键词搜索**
   - 先用标签过滤
   - 再用全文搜索
3. **从知识层入手**
   - 先找到对应的概念页/指南页
   - 从页面的"相关"链接深入
4. **下钻到原子层**
   - 需要细节时查看具体卡片
5. **补充缺失**
   - 找不到内容时，记录为缺口
   - 安排时间补充

**查询优化技巧：**
- 每个概念页设置 3-5 个核心标签
- 常用查询保存为搜索书签
- 定期整理同义词和别名（重定向页面）

### 工作流 3：整理（Refine）——持续提升知识库质量

**适用场景：** 每周/每月的知识库维护

**步骤：**
1. **处理 #待整理 标签**
   - 回顾快速摄入的内容
   - 完善格式和关联
2. **检查重复内容**
   - 搜索相似标题
   - 合并重复的概念页
3. **更新过时内容**
   - 检查工具版本是否更新
   - 更新数据和事实
4. **优化关联**
   - 添加缺失的双向链接
   - 清理无效链接
5. **STE 质量抽检**
   - 随机抽取 5 个页面
   - 用 STE 规则检查
   - 记录质量评分

# 第 4 篇：Agent 篇——让 Agent 输出符合 STE 规范

## 4.1 为什么 Agent 需要 STE 约束

### Agent 输出的 3 个典型问题

**问题 1：输出不稳定**
- 同一个 Agent，同样的输入，输出格式差别很大
- 有时候啰嗦，有时候太简略
- 关键信息有时候漏掉

**问题 2：Agent 之间通信不畅**
- Agent A 的输出，Agent B 理解错了
- 信息在传递中失真
- 多 Agent 协作效率低

**问题 3：难以调试和评估**
- 不知道 Agent 的输出质量好不好
- 无法量化改进效果
- 问题定位困难

### STE 如何解决这些问题

| 问题 | STE 解决方案 |
|-----|-------------|
| 输出不稳定 | 明确的规则 = 可预期的输出 |
| 通信失真 | 无歧义的表达 = 信息传递准确 |
| 难以评估 | 可检查的规则 = 可量化的质量评分 |

### 一个直观的类比

没有 STE 约束的 Agent 就像：
- 一个没有操作手册的工厂
- 每个工人按自己的方式干活
- 产品质量全凭心情

有 STE 约束的 Agent 就像：
- 有严格 SOP 的流水线
- 每个环节有明确的质量标准
- 产出稳定，可预测，可优化

## 4.3 STE 自检流程

### 自检的 5 个步骤

让 Agent 在输出答案后，自己执行以下检查：

```
## STE 自检流程

步骤 1：句子长度检查
- 统计最长句子的字数
- 如果超过 25 字，拆分它

步骤 2：段落长度检查
- 检查每段的句子数量
- 如果超过 3 句，拆分段落

步骤 3：语态检查
- 统计被动语态句子的比例
- 如果超过 10%，改为主动语态

步骤 4：信息密度检查
- 删除以下内容：
  - 客套话（"非常感谢""希望能帮到你"）
  - 连接词（"然而""因此""综上所述"）
  - 重复信息
  - 无意义的填充语

步骤 5：一致性检查
- 检查同一概念是否用了不同的词
- 统一术语
- 检查代词是否有明确指代
```

### 自检的实现方式

**方式 1：在系统提示词中要求自检**
- 最简单的方式
- 适合所有支持系统提示词的平台
- 效果取决于模型能力

**方式 2：两阶段调用**
- 第一阶段：生成答案
- 第二阶段：用另一个 Prompt 专门做 STE 检查和改写
- 质量更高，但成本也更高

**两阶段调用的第二阶段 Prompt：**
```
请检查以下内容是否符合 STE 规范，并进行修改。

检查清单：
1. 句子是否过长（>25字）
2. 段落是否过长（>3句）
3. 是否使用了被动语态
4. 是否有冗余套话
5. 术语是否一致
6. 代词是否明确

请输出修改后的版本，并说明做了哪些修改。

待检查内容：
{第一阶段的输出}
```

**方式 3：专用 STE 检查 Agent**
- 创建一个专门的"STE 检查员"Agent
- 所有其他 Agent 的输出都先经过它检查
- 适合多 Agent 系统

## 4.4 STE 评分系统

### 评分维度和权重

| 维度 | 权重 | 满分 | 说明 |
|-----|------|------|------|
| 句子简洁度 | 20% | 20 分 | 句子长度、句子结构复杂度 |
| 段落结构 | 15% | 15 分 | 段落长度、列表使用 |
| 语态规范 | 15% | 15 分 | 主动语态比例 |
| 信息密度 | 20% | 20 分 | 有效信息占比、冗余程度 |
| 术语一致性 | 15% | 15 分 | 同一概念用词一致 |
| 格式清晰度 | 15% | 15 分 | 列表、表格、层级使用 |
| **总分** | **100%** | **100 分** | |

### 评分标准详解

#### 句子简洁度（20 分）

| 得分 | 标准 |
|-----|------|
| 18-20 分 | 90% 以上句子 ≤ 20 字，最长不超过 25 字 |
| 14-17 分 | 70% 以上句子 ≤ 25 字，最长不超过 35 字 |
| 10-13 分 | 50% 以上句子 ≤ 25 字，存在少量长句 |
| < 10 分 | 大量长句，结构复杂 |

#### 段落结构（15 分）

| 得分 | 标准 |
|-----|------|
| 13-15 分 | 所有段落 ≤ 3 句，适当使用列表 |
| 10-12 分 | 大部分段落 ≤ 4 句，列表使用合理 |
| 7-9 分 | 存在一些长段落，列表使用不足 |
| < 7 分 | 大段文字，几乎没有列表 |

#### 语态规范（15 分）

| 得分 | 标准 |
|-----|------|
| 13-15 分 | 主动语态占比 ≥ 90% |
| 10-12 分 | 主动语态占比 70%-90% |
| 7-9 分 | 主动语态占比 50%-70% |
| < 7 分 | 被动语态为主 |

#### 信息密度（20 分）

| 得分 | 标准 |
|-----|------|
| 18-20 分 | 几乎没有套话，每句都有信息量 |
| 14-17 分 | 少量连接词和过渡语，不影响阅读 |
| 10-13 分 | 有一定冗余，可压缩 20%-30% |
| < 10 分 | 大量套话，有效信息不足 50% |

#### 术语一致性（15 分）

| 得分 | 标准 |
|-----|------|
| 13-15 分 | 术语完全统一，没有同义词混用 |
| 10-12 分 | 基本一致，有少量不影响理解的变化 |
| 7-9 分 | 存在一些术语不一致 |
| < 7 分 | 同一概念多种说法，混乱 |

#### 格式清晰度（15 分）

| 得分 | 标准 |
|-----|------|
| 13-15 分 | 层级分明，列表表格使用恰当 |
| 10-12 分 | 结构清晰，格式基本规范 |
| 7-9 分 | 结构不够清晰，需要梳理 |

## 4.5 多 Agent 场景下的 STE 规范传递

### 为什么多 Agent 更需要 STE

在多 Agent 系统中：
- Agent A 的输出 = Agent B 的输入
- 信息每经过一个 Agent，就可能有一次失真
- 没有规范的话，3 次传递后信息可能完全走样

**STE 的作用：** 为 Agent 之间的通信提供"标准协议"。

### 多 Agent STE 规范传递策略

#### 策略 1：所有 Agent 共享系统提示词

最简单的做法：
- 每个 Agent 的系统提示词都包含 STE 规范
- 输出格式统一

**优点：** 简单，易实现
**缺点：** 每个 Agent 都要"学"一遍 STE，浪费 token

#### 策略 2：设置 STE 协调员 Agent

架构：
```
用户 → 任务分配 Agent → [专业 Agent A, 专业 Agent B] → STE 协调员 → 用户
```

STE 协调员的职责：
1. 检查所有 Agent 的输出是否符合 STE 规范
2. 统一术语和格式
3. 合并多个 Agent 的输出
4. 输出最终的 STE 风格结果

**优点：** 质量有保障，专业 Agent 可以更自由地思考
**缺点：** 增加一次调用，延迟更高

#### 策略 3：消息格式标准化

定义 Agent 之间的消息格式：

```json
{
  "message_type": "task_result / question / clarification",
  "sender": "agent_name",
  "receiver": "agent_name",
  "content": {
    "summary": "一句话总结",
    "key_points": ["要点1", "要点2", "要点3"],
    "details": "详细内容（STE 格式）",
    "action_items": [
      {"task": "任务描述", "owner": "负责人", "deadline": "截止时间"}
    ]
  },
  "confidence": 0.9,
  "ste_score": 8.5
}
```

**优点：**
- 结构化程度最高
- 便于程序处理
- 信息传递最准确

**缺点：**
- 实现成本高
- 不够灵活

### 推荐架构

对于大多数场景，推荐策略 2（STE 协调员）：

```
┌─────────────┐
│   用户输入   │
└──────┬──────┘
       │
       ▼
┌─────────────┐     ┌─────────────┐
│  主控 Agent │────▶│ 专业 Agent A │
│  (任务分配)  │     └─────────────┘
└──────┬──────┘     ┌─────────────┐
       ├───────────▶│ 专业 Agent B │
       │            └─────────────┘
       ▼
┌─────────────┐
│ STE 协调员   │
│ (质量检查+   │
│  格式统一+   │
│  结果整合)   │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  STE 输出    │
└─────────────┘
```

### 实施步骤

1. **第一步：给主控 Agent 加上 STE 系统提示词**
   - 确保入口和出口都是 STE 格式

2. **第二步：给专业 Agent 加上基本 STE 要求**
   - 不需要太严格，保证信息准确即可

3. **第三步：增加 STE 协调员**
   - 专门负责质量检查和格式统一
   - 使用第 4.3 节的自检流程

4. **第四步：定义 Agent 间消息格式**
   - 先从关键环节开始
   - 逐步推广到所有 Agent 通信

# 第 5 篇：代码篇——STE 在技术写作中的应用

## 5.1 代码注释的 STE 规范

### 为什么代码注释需要 STE

代码注释的问题：
- 注释写得比代码还难读
- 说了等于没说（`i++ // i 加 1`）
- 过时的注释比没有注释更糟糕
- 新人看不懂老代码的注释

STE 风格的注释：
- 一句话说清楚"为什么"
- 不说"是什么"（代码本身已经说明）
- 简洁、准确、可验证

### 注释的 STE 规则

| 规则 | 说明 |
|-----|------|
| 只写"为什么"，不写"是什么" | 代码本身说明做了什么 |
| 单行注释 ≤ 30 字 | 长注释拆成多行 |
| 不用"可能""也许"等模糊词 | 要么确定，要么不写 |
| 说明前置条件和副作用 | 这些是代码看不出来的 |
| 及时更新注释 | 修改代码时同步更新注释 |
| TODO 必须包含日期和负责人 | `// TODO(张三, 2024-06): 重构此函数` |

### 对比示例

**差的注释：**
```javascript
// 这个函数用来处理用户的登录请求，它会先验证用户输入的信息是否有效，
// 然后查询数据库看看有没有这个用户，如果有的话再验证密码是否正确，
// 最后生成一个 token 返回给前端。如果有任何一步出错了就返回错误信息。
function login(username, password) {
  // 检查用户名和密码
  if (!username || !password) {
    // 返回参数错误
    return { error: "参数错误" };
  }
  // 查询用户
  const user = db.findUser(username);
  // ...
}
```

**STE 风格注释：**
```javascript
// 用户登录验证。返回 token 或错误对象。
// 前置条件：username、password 为非空字符串
// 副作用：更新用户最后登录时间
function login(username, password) {
  // 参数校验：拒绝空值
  if (!username || !password) {
    return { error: "参数错误" };
  }
  
  // 查询用户信息（缓存优先）
  const user = db.findUser(username);
  // ...
}
```

### 不同类型注释的 STE 写法

**文件头注释：**
```python
"""
用户认证模块。

功能：
1. 用户登录/登出
2. Token 生成与验证
3. 权限检查

依赖：
- db.py：数据库操作
- crypto.py：加密工具
"""
```

**函数注释：**
```python
def calculate_discount(price: float, level: str) -> float:
    """
    计算会员折扣价。
    
    参数：
        price: 原价，必须大于 0

## 5.4 错误信息的 STE 写法

### 好的错误信息的 3 要素

1. **哪里错了** —— 具体的位置或参数
2. **为什么错了** —— 根本原因
3. **怎么改** —— 明确的修复步骤

### 对比示例

| 差的错误信息 | STE 风格错误信息 |
|-------------|----------------|
| 操作失败 | 操作失败：用户 ID 不能为空<br>原因：请求中缺少 user_id 字段<br>解决：在请求体中添加 user_id 参数 |
| 系统错误 | 系统错误：数据库连接超时<br>原因：数据库服务不可用（503）<br>解决：请稍后重试，或联系管理员 |
| 格式不正确 | 格式错误：email 字段格式无效<br>原因：输入值 "abc" 不是合法邮箱<br>解决：请输入格式为 user@example.com 的邮箱 |

### 错误信息 STE 规则

1. **不使用模糊词汇**
   - ❌ "出错了"
   - ✅ "用户 ID 参数缺失"

2. **给出具体值**
   - ❌ "参数超出范围"
   - ✅ "参数 age 值为 200，允许范围 0-150"

3. **给出解决方案**
   - ❌ "请检查后重试"
   - ✅ "请将 age 修改为 0-150 之间的整数"

4. **包含错误码**
   - 便于程序识别和处理
   - 便于用户搜索解决方案

## 5.5 代码评审意见的 STE 表达

### 为什么代码评审需要 STE

代码评审的常见问题：
- 意见模糊，作者不知道怎么改
- 语气不当，引发争论
- 评论太长，没人看

STE 风格的评审意见：
- 具体、可执行
- 对事不对人
- 清晰、简洁

### 评审意见的 STE 模板

**格式：**
```
[问题类型] {具体描述}

原因：{为什么这是个问题}
建议：{具体怎么改}
严重程度：[严重 / 建议 / 可选]
```

**问题类型：**
- Bug：功能错误
- 性能：性能问题
- 安全：安全隐患
- 可读性：代码难以理解
- 规范：不符合代码规范
- 架构：设计问题

### 对比示例

| 差的评审意见 | STE 风格评审意见 |
|-------------|----------------|
| 这里写得不太好，改一下吧 | [可读性] 这个函数有 80 行，嵌套 5 层<br>原因：难以理解和维护<br>建议：拆分为 3 个小函数，每个函数不超过 20 行<br>严重程度：建议 |
| 性能会不会有问题？ | [性能] 循环中调用数据库查询<br>原因：循环 100 次就会产生 100 次数据库查询，响应慢<br>建议：改为批量查询，一次查出所有数据<br>严重程度：严重 |
| 变量名不太好 | [规范] 变量名 `data` 含义不明确<br>原因：`data` 没有说明是什么数据<br>建议：改为 `userList` 或 `userRecords`<br>严重程度：建议 |
| 你这样写有问题 | [Bug] 边界情况未处理：输入为空数组时返回 undefined<br>原因：函数假设数组非空，但调用方可能传入空数组<br>建议：函数开头添加空数组检查，返回空结果<br>严重程度：严重 |

### 评审意见的语气原则

1. **对事不对人**
   - ❌ "你这里写错了"
   - ✅ "这段代码在 X 情况下会出错"

2. **用疑问句代替否定句**
   - ❌ "这样不行"
   - ✅ "如果考虑 X 情况，是否需要补充处理？"

3. **给出具体建议，不是只说问题**
   - ❌ "性能不好"
   - ✅ "建议用 Map 替代数组查找，复杂度从 O(n) 降到 O(1)"

4. **区分严重程度**
   - 严重：必须修改
   - 建议：建议修改，不影响功能
   - 可选：个人偏好，可讨论

## 6.1 文章/报告写作的 STE 应用

### STE 不是让你写"干巴巴"的文字

很多人误以为 STE 就是把文章写得像说明书一样干巴巴。实际上，STE 的核心是"清晰"，而不是"无趣"。

**对于文章和报告：**
- 核心信息用 STE 风格（确保清晰）
- 过渡和叙事可以用普通风格（确保流畅）
- 推荐浓度：50% STE

### STE 文章结构法

#### 方法 1：结论先行（BLUF 原则）

BLUF = Bottom Line Up Front（结论放在最前面）

**普通结构：**
> 背景 → 分析 → 论证 → 结论

**STE 结构：**
> 结论 → 理由 → 证据 → 补充说明

**示例：**

| 普通写法 | STE 写法 |
|---------|---------|
| 最近我们研究了几种新的技术方案，包括 A 方案、B 方案和 C 方案。经过两周的测试和评估，我们发现各有优缺点。A 方案性能好但成本高，B 方案成本低但性能一般，C 方案比较均衡但需要更多学习成本。综合考虑下来... | **结论：推荐采用 C 方案。**<br><br>**三个理由：**<br>1. 性能满足当前需求（QPS 达标）<br>2. 成本在预算范围内（超支 5%）<br>3. 团队学习成本可控（2 周上手）<br><br>**各方案对比：**<br>| 方案 | 性能 | 成本 | 学习成本 |<br>|-----|------|------|---------|<br>| A | 高 | 高（+30%）| 低 |<br>| B | 中 | 低 | 低 |<br>| C | 中高 | 中（+5%）| 中 |<br><br>**风险和应对：**<br>- 学习曲线较陡 → 安排培训和结对编程 |

#### 方法 2：信息分层法

把文章内容分为三层，每层信息密度不同：

| 层级 | 内容 | STE 浓度 | 读者 |
|-----|------|---------|------|
| 第一层 | 标题 + 摘要 + 结论 | 100% | 只看结论的人 |
| 第二层 | 各节要点 + 图表 | 80% | 快速浏览的人 |
| 第三层 | 详细论证 + 案例 | 50% | 需要深入了解的人 |

**好处：**
- 不同需求的读者各取所需
- 读者可以选择阅读深度
- 作者也更容易组织内容

#### 方法 3：列表化表达

能用列表说清楚的，就不用段落。

**适用场景：**
- 列举原因、特点、步骤
- 展示优缺点
- 总结要点

**转换技巧：**
1. 找出段落中的名词短语
2. 每个名词短语变成一个列表项
3. 给每个列表项加一个简短说明

### 长文写作的 STE 工作流

1. **列大纲** —— 用 STE 风格列出所有要点
2. **填充内容** —— 先不管文风，把内容写出来
3. **STE 化改写** —— 按照 STE 规则精简和结构化
4. **润色流畅度** —— 加入必要的过渡，保证可读性
5. **自检** —— 用第 8 篇的自检 5 步法检查

## 6.3 演示文稿的 STE 原则

### 为什么 PPT 需要 STE

PPT 的本质是"视觉化的要点展示"，不是"文档搬家"。
STE 风格和 PPT 的理念高度契合：
- 简洁
- 要点化
- 信息密度高

### STE 风格 PPT 的 5 条原则

1. **一页一个核心信息**
   - 不要把多件事塞到一页
   - 标题就是结论

2. **文字越少越好**
   - 每页不超过 6 行字
   - 每行不超过 15 个字
   - 用关键词，不用完整句子

3. **用图表代替文字**
   - 对比用表格
   - 流程用流程图
   - 数据用图表

4. **结构清晰，层层递进**
   - 目录页明确结构
   - 每部分有小结页
   - 最后有总结页

5. **演讲词和 PPT 分离**
   - PPT 只放要点
   - 详细内容放在演讲者备注里

### 对比示例

| 差的 PPT 页面 | STE 风格 PPT 页面 |
|-------------|------------------|
| **微服务架构的优势**<br><br>微服务架构是一种将单体应用拆分为多个小型服务的架构方式。每个服务运行在自己的进程中，服务之间通过轻量级的通信机制进行交互。这些服务围绕业务能力进行构建，并且可以通过自动化部署机制独立部署。由于每个服务都是独立的，因此可以使用不同的编程语言和不同的数据存储技术。 | **微服务的 4 个核心优势**<br><br>1. **独立部署**<br>   一个服务更新不影响其他服务<br><br>2. **技术异构**<br>   不同服务可以用不同技术栈<br><br>3. **弹性扩展**<br>   只扩展有压力的服务<br><br>4. **团队自治**<br>   小团队可以独立负责一个服务 |

   - 标题（一句话）

## 6.4 知识萃取：把经验变成 STE 风格的可复用资产

- 信息密度高，不浪费时间

## 6.5 个人笔记的 STE 整理法

### 为什么笔记需要 STE

很多人的笔记问题：
- 当时记的时候很爽，回头看完全看不懂
- 同一个主题分散在 N 个地方
- 越记越多，但用不起来

STE 笔记的好处：
- 什么时候看都能懂
- 信息密度高，不占地方
- 容易搜索和关联

### 三种笔记的 STE 写法

#### 1. 读书/学习笔记

**STE 笔记法：**
1. 不抄原文，用自己的话（短句）
2. 每章提炼 3-5 个核心观点
3. 每个观点不超过 30 字
4. 标记金句（原文引用）
5. 写下自己的思考和应用

**STE 会议笔记法：**
1. 不做逐字记录
2. 只记决策、行动项、待确认问题
3. 用列表，不用段落
4. 会后 24 小时内整理

**STE 灵感笔记法：**
1. 快速记录核心想法（1 句话）
2. 补充背景和为什么重要
3. 标记类型（产品/技术/写作/其他）
4. 定期review，有用的深化，没用的删除

### 笔记整理的 STE 原则

1. **一笔记一事**
   - 一篇笔记只讲一个主题
   - 主题太多就拆分

2. **命名清晰**
   - 标题就是内容的概括
   - 不用"新建笔记""笔记1"这种名字

3. **定期整理**
   - 每周整理一次零散笔记
   - 每月 review 一次旧笔记
   - 删除没用的，合并重复的

4. **标签克制**
   - 标签不是越多越好
   - 每个笔记 3-5 个标签最合适
   - 建立标签体系，不随便新增

# 第 7 篇：工具篇——STE 写作辅助工具

## 7.1 LLM 作为 STE 检查员

### 为什么用 LLM 做 STE 检查

STE 规则虽然明确，但人工检查费时费力。LLM 可以：
- 秒级完成检查
- 同时检查多个维度
- 直接给出修改建议
- 成本极低

### STE 检查员 Prompt

```
你是一名 STE（简化技术英语）检查员。请检查以下内容是否符合 STE 规范。

检查维度：
1. 句子简洁度：句子是否过长（>25字），结构是否复杂
2. 段落结构：段落是否过长（>3句），是否应使用列表
3. 语态规范：被动语态是否过多（>10%）
4. 信息密度：是否有套话、冗余、重复
5. 术语一致性：同一概念是否用词一致
6. 代词明确：代词（它、这、那）是否有明确指代
7. 格式清晰：列表、表格、层级是否恰当

输出格式：
---
STE 评分：X/100
各维度得分：
- 句子简洁度：X/20
- 段落结构：X/15
- 语态规范：X/15
- 信息密度：X/20
- 术语一致性：X/15
- 格式清晰度：X/15

主要问题：
1. {问题描述} → {修改建议}
2. {问题描述} → {修改建议}
...

修改后的版本：
{STE 风格的改写版本}
---

待检查内容：
{在此粘贴待检查的文本}
```

### 使用场景

1. **写完后检查** —— 写完任何东西都先丢给 LLM 过一遍
2. **学习 STE** —— 对比原文和修改版，学习 STE 写法
3. **批量处理** —— 用脚本批量检查大量文档的 STE 质量

### 局限性

- LLM 可能会误解原文意思，修改后信息有偏差
- 对于专业术语，LLM 可能不知道正确的统一用法
- 需要人工审核修改结果

**建议：** LLM 作为辅助工具，最终质量由人把控。

## 7.2 自动检查脚本

### Python STE 检查器（基础版）

以下是一个简单的 Python 脚本，可以自动检测一些常见的非 STE 特征。

```python
"""
STE 风格自动检查工具（中文）
检查内容：
1. 长句检测（>25字）
2. 长段落检测（>3句）
3. 被动语态检测
4. 套话/冗余词检测
5. 模糊代词检测
"""

import re
from typing import Dict, List, Tuple


def split_sentences(text: str) -> List[str]:
    """按中文句号、问号、感叹号拆分句子"""
    sentences = re.split(r'[。！？\n]', text)
    return [s.strip() for s in sentences if s.strip()]


def split_paragraphs(text: str) -> List[str]:
    """按空行拆分段落"""
    paragraphs = re.split(r'\n\s*\n', text)
    return [p.strip() for p in paragraphs if p.strip()]


def check_long_sentences(sentences: List[str], max_len: int = 25) -> List[Tuple[int, str, int]]:
    """检测长句，返回 (序号, 句子, 长度)"""
    result = []
    for i, s in enumerate(sentences):
        if len(s) > max_len:
            result.append((i + 1, s, len(s)))
    return result


def check_long_paragraphs(paragraphs: List[str], max_sentences: int = 3) -> List[Tuple[int, int]]:
    """检测长段落，返回 (段落序号, 句子数)"""
    result = []
    for i, p in enumerate(paragraphs):
        sentences = split_sentences(p)
        if len(sentences) > max_sentences:
            result.append((i + 1, len(sentences)))
    return result


# 被动语态常见模式
PASSIVE_PATTERNS = [
    r'被\w+',
    r'受到\w+',
    r'遭到\w+',
    r'得以\w+',
    r'由\w+所',
    r'为\w+所',
]


def check_passive_voice(sentences: List[str]) -> List[Tuple[int, str]]:
    """检测被动语态句子"""
    result = []
    for i, s in enumerate(sentences):
        for pattern in PASSIVE_PATTERNS:
            if re.search(pattern, s):
                result.append((i + 1, s))
                break
    return result


# 套话/冗余词列表
FILLER_WORDS = [
    '非常', '十分', '相当', '比较', '特别', '格外',
    '其实', '事实上', '实际上', '基本上', '大概',
    '众所周知', '不言而喻', '毫无疑问',
    '综上所述', '总而言之', '由此可见',
    '值得一提的是', '需要指出的是',
    '在某种程度上', '在一定程度上',
    '为了', '以便', '从而', '因此', '然而',
]


def check_filler_words(text: str) -> List[Tuple[str, int]]:
    """检测套话和冗余词，返回 (词语, 出现次数)"""
    result = []
    for word in FILLER_WORDS:
        count = text.count(word)
        if count > 0:
            result.append((word, count))
    return result


# 模糊代词
VAGUE_PRONOUNS = ['它', '这', '那', '其', '该']


def check_vague_pronouns(sentences: List[str]) -> List[Tuple[int, str]]:
    """检测可能有歧义的代词使用"""
    result = []
    for i, s in enumerate(sentences):
        # 句子开头用"这""那"可能指代不明
        if re.match(r'^[这那它其该]', s) and len(s) < 15:
            result.append((i + 1, s))
    return result


def ste_check(text: str) -> Dict:
    """执行完整的 STE 检查"""
    sentences = split_sentences(text)
    paragraphs = split_paragraphs(text)
    
    long_sentences = check_long_sentences(sentences)
    long_paragraphs = check_long_paragraphs(paragraphs)
    passive_sentences = check_passive_voice(sentences)
    filler_words = check_filler_words(text)
    vague_pronouns = check_vague_pronouns(sentences)
    
    # 计算分数（简化版）
    total_sentences = len(sentences)
    long_ratio = len(long_sentences) / max(total_sentences, 1)
    passive_ratio = len(passive_sentences) / max(total_sentences, 1)
    
    sentence_score = max(0, 20 - long_ratio * 40)
    voice_score = max(0, 15 - passive_ratio * 30)
    filler_count = sum(c for _, c in filler_words)
    density_score = max(0, 20 - filler_count * 2)
    
    total = sentence_score + voice_score + density_score + 30  # 其他维度暂给满分
    
    return {
        "score": round(total, 1),
        "stats": {
            "total_sentences": total_sentences,
            "total_paragraphs": len(paragraphs),
            "long_sentence_count": len(long_sentences),
            "passive_sentence_count": len(passive_sentences),
            "filler_word_count": filler_count,
        },
        "issues": {
            "long_sentences": long_sentences,
            "long_paragraphs": long_paragraphs,
            "passive_voice": passive_sentences,
            "filler_words": filler_words,
            "vague_pronouns": vague_pronouns,
        }
    }


def print_report(result: Dict):
    """打印检查报告"""
    print("=" * 50)
    print(f"STE 检查报告")
    print("=" * 50)
    print(f"总分：{result['score']}/100")
    print()
    
    stats = result['stats']
    print(f"句子总数：{stats['total_sentences']}")
    print(f"段落总数：{stats['total_paragraphs']}")
    print(f"长句数量：{stats['long_sentence_count']}")
    print(f"被动语态数量：{stats['passive_sentence_count']}")
    print(f"套话数量：{stats['filler_word_count']}")
    print()
    
    issues = result['issues']
    
    if issues['long_sentences']:
        print("⚠️  长句列表：")
        for idx, s, length in issues['long_sentences'][:5]:
            print(f"  第{idx}句 ({length}字): {s[:30]}...")
        print()
    
    if issues['passive_voice']:
        print("⚠️  被动语态句子：")
        for idx, s in issues['passive_voice'][:5]:
            print(f"  第{idx}句: {s[:30]}...")
        print()
    
    if issues['filler_words']:
        print("⚠️  套话/冗余词：")
        for word, count in issues['filler_words']:
            print(f"  {word}: {count} 次")
        print()
    
    if issues['vague_pronouns']:
        print("⚠️  可能指代不明的句子：")
        for idx, s in issues['vague_pronouns'][:5]:
            print(f"  第{idx}句: {s}")
        print()


# 使用示例
if __name__ == "__main__":
    test_text = """
    人工智能是一种非常重要的技术，它在很多领域都得到了广泛的应用。
    事实上，人工智能的发展历史相当悠久，可以追溯到上世纪50年代。
    众所周知，人工智能的核心是机器学习，而机器学习的核心是算法和数据。
    综上所述，我们应该加强对人工智能的研究和投入。
    该技术受到了全球各大科技公司的重视。
    这是不言而喻的。
    """
    
    result = ste_check(test_text)
    print_report(result)
```

3. 查看检查报告

## 8.3 STE 浓度调节指南

### 什么时候用什么浓度

| 场景 | 推荐浓度 | 操作提示 |
|-----|---------|---------|
| **操作手册 / 安全指南** | 100% | 严格执行所有规则 |
| **API 文档 / 技术规范** | 100% | 精确无歧义 |
| **Agent 系统提示词** | 100% | 指令清晰 |
| **Agent 之间通信** | 100% | 结构化消息 |
| **知识库概念页** | 80% | 信息密度优先 |
| **技术教程** | 80% | 步骤清晰 |
| **日常 AI 对话** | 80% | 效率优先 |
| **工作邮件** | 80% → 50% | 专业且不失礼貌 |
| **会议纪要** | 80% | 要点明确 |
| **技术文章 / 博客** | 50% | 兼顾可读性 |
| **产品方案 / 报告** | 50% | 专业流畅 |
| **科普内容** | 50% | 通俗易懂 |
| **创意写作 / 小说** | 0% | STE 不适用 |

### 浓度调节技巧

**提高浓度（从 50% 到 80%）：**
1. 删除所有形容词和副词
2. 把段落拆成列表
3. 被动语态改主动语态
4. 删除连接词和过渡语
5. 每段控制在 3 句以内

**降低浓度（从 80% 到 50%）：**
1. 加入必要的过渡句
2. 适当展开解释
3. 增加例子和类比
4. 保留一些礼貌用语
5. 段落可以稍长一些

## 8.4 STE 自检 5 步法

写完任何内容后，按以下 5 步检查：

### 第 1 步：删套话
- 找出所有"非常""十分""众所周知""综上所述"等词
- 直接删除
- 如果删除后句子不通顺，调整语序

### 第 2 步：拆长句
- 找出所有超过 25 字的句子
- 每句拆成 2-3 个短句
- 拆分点：逗号、"和""并且""然后"等连接词

### 第 3 步：改语态
- 找出所有被动语态（"被""受到""遭到""由...所"）
- 改为主动语态
- 方法：把动作的执行者放到主语位置

### 第 4 步：换代词
- 找出所有"它""这""那""其""该"
- 替换为具体名词
- 如果前面刚说过，可以用"上述 X""该 X"等明确指代

### 第 5 步：结构优化
- 能用列表的不用段落
- 能做表格的不做对比描述
- 结论放到最前面
- 每段不超过 3 句话

### 自检时间估计

| 内容长度 | 预计自检时间 |
|---------|-------------|
| 100 字以内 | 1 分钟 |
| 500 字以内 | 3-5 分钟 |
| 1000 字以内 | 10 分钟 |
| 长文（逐篇检查） | 每篇 5-10 分钟 |

**建议：** 先养成习惯，每次写完花 1 分钟自检。熟练后速度会越来越快。
