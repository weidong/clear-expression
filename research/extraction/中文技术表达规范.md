# 中文技术表达规范 v1.0

> 依据：ASD-STE100 Issue 9（53 条规则 + 8 条通用建议）、中文翻译、AI 手册、你的《中文 STE 使用规划和应用手册》、`ste-checker.py`。
> 定位：**不是 STE 的中文翻译，而是给中文用的可执行规范。**
> 约定：标注 `[STE]` 的是官方规则；标注 `[中文]` 的是为中文新增的适配规则；标注 `[待定]` 的需要你拍板。

---

## 0. 为什么不能直接翻译 STE

STE 是英语规范。它有几条核心规则在中文里**没有对应物**，照搬会失效：

| STE 规则 | 中文的问题 |
|---|---|
| 每句 ≤20 词 / ≤25 词 | 汉语没有词边界，计"词"不可操作 → 必须改成计"字"或计"信息点" |
| 用冠词 the/a 区分特指 | 汉语没有冠词，规则失效 |
| 禁用 -ing、区分过去分词 | 汉语没有形态变化 |
| 多词名词 ≤3 词 | 汉语算"定语项"，规则要重写 |
| 连字符构词 | 汉语没有构词连字符 |
| 被动语态判据（by whom） | 汉语"被/由/受"用法不同，且常省略施动者 |

**结论：约 80% 的思想可迁移，具体判据必须重写。** 本文档做的就是这件事。

## 1. 三档文体（不是"浓度"，是文体）

`[中文]` 把"浓度 100/80/50"这种说法换掉——STE 原文没有"浓度"概念，那是你手册里的创造，概念上不准确。改用**文体**分类，因为规则本来就按文体分。

| 档位 | 用途 | 报警线 | 错误线 | 段落 | 允许修辞 |
|---|---|---|---|---|---|
| **A. 程序性** | 操作步骤、方案的实施部分、给 AI 的指令 | > 20 字 | > 30 字 | ≤ 3 句 | 禁止 |
| **B. 描述性** | 原理说明、技术文档、知识卡片 | > 25 字 | > 35 字 | ≤ 3 句 | 极少量 |
| **C. 可读性** | 公众号、自媒体 | > 40 字 | > 55 字 | ≤ 4 句 | 允许，但不得牺牲准确 |

> `[数据]` 阈值来自你 240 篇、28.8 万字语料的实测：平均句长 20.8 字，中位 13 字，**90 分位 37 字，95 分位 55 字**。
> 超过 25 字的句子占 20.6%——所以 C 档不能卡 25，会把你 1/5 的句子判违规。C 档卡在 40，只拉回最长的 10%。详见《learn-ai 语料分析报告》。

> `[STE]` 官方原值：程序性 ≤20 **词**，描述性 ≤25 **词**，段落 ≤6 句。
> `[中文]` 折算：词数改为字数，且取偏严的值。理由见第 9 章（材料冲突 C3）。

**核心原则不变**：越靠近"照做"，越严格；越靠近"阅读"，越宽松。**但"一句话只说一件事"三档都不放松。**

#### 四条使用规则

**规则 V1 `[中文]`：一个动作一个词，不许同义混用。**

| 禁止 | 改用 |
|---|---|
| 搞、弄、整、处理、拿下、搞定 | 按实际动作选：修改 / 删除 / 替换 / 调整 |
| 看一下、查一下、过一下 | 检查 / 核对 / 验证 |
| 弄好、搞定、完成一下 | 完成 / 提交 / 发布 |

**规则 V2 `[中文]`：动作词优先，禁止"虚动词 + 名词"。**

这是中文最常见、最伤清晰度的毛病：

| ❌ 名词化 | ✅ 直接动作 |
|---|---|
| 对系统进行测试 | 测试系统 |
| 做出判断 | 判断 |
| 予以处理 | 处理（或写明具体动作） |
| 加以说明 | 说明 |
| 进行优化 | 优化 |
| 开展检查工作 | 检查 |

**禁用虚动词**：进行、做出、予以、加以、开展、实施（除非"实施"是唯一准确词）。

**规则 V3 `[STE]`：名词不作动词，动词不作名词。**

| ❌ | ✅ |
|---|---|
| 油一下钢表面 | 在钢表面涂油 |
| 给孔一个 0.2 英寸的铰 | 把孔铰到 0.2 英寸 |
| 对笔记本电池做个检查 | 检查笔记本电池 |

**规则 V4 `[STE]`：一词一义。** 同一个词只表达一个意思，且全篇不变。

`[STE]` 原文典型反例：`follow` 的批准义只有"跟在后面"，所以 `Follow the safety instructions` 不合规，应写 `Obey the safety instructions`。中文同理：「跟进」不能既表示"跟踪进度"又表示"继续处理"。

### 2.2 名词与术语

**规则 N1 `[STE]`：一个东西只有一个名字，全篇不变。**
反例：`伺服控制组件 / 作动筒 / 控制单元` 混用 → 全篇统一「作动筒」。

**规则 N2 `[中文]`：名词短语的定语成分 ≤3 个。**

| ❌ | ✅ |
|---|---|
| 跑道灯连接电阻校准作业规程 | 跑道灯连接处电阻的校准方法 |
| 基于深度学习的自然语言处理模型微调方法 | 自然语言处理模型的微调方法（基于深度学习） |

判定：数"的"字前后的修饰成分。超过 3 个，用"的 / 对 / 在"拆开，或改成从句。

**规则 N3 `[中文]`：术语表是唯一权威。**
写法统一由术语表决定，不靠记忆。术语表三列：`概念 | 统一写法 | 禁止写法`。

**规则 N4 `[STE]`：技术名词可以作修饰语，不能作动词。**
✅「配置文件」作名词；❌「配置一下服务器」→ ✅「修改服务器配置」。

### 2.3 禁用词与替换

`[中文]` 三张黑名单，全部来自 `ste-checker.py` 的实际实现，可直接自动化检查。

**① 模糊词（hedging）——一个都不留**

```
强（出现即违规）：可能、大概、也许、或许、好像、似乎、看起来、想必、不一定、不太可能
弱（每段≥3 个违规）：最好、可以考虑、一些、若干、之类的、类似的、等等、非常、极其、相当、十分、无比、颇为
```

> `[数据]` **「可能」是你语料里最高频的模糊词：320 次，11.1/万字**，比「进行 + 做出」加起来还多 3 倍。
> 这是你最该改的一个词，优先于所有其他规则。
>
> 例外：在"（建议…""（推荐…"这类明确标注的场景里可保留——这是脚本里的白名单逻辑。

**② 语气助词——句末不出现**

```
吧、呢、啊、哦、嘛、呀、哇、啦、咯、哩
```

**③ 成语习语——技术文本不用**

```
事半功倍、对症下药、举足轻重、不言而喻、显而易见、众所周知、毫无疑问、
如虎添翼、如火如荼、方兴未艾、雨后春笋、冰山一角、九牛一毛、综上所述、总而言之……
```

> 成语的问题不是"不好"，而是**歧义**：它省略了逻辑关系，读者要自己补。技术文本不能要求读者补。

### 2.4 术语表（12 条，语料提取）

`[数据]` 从你的语料里统计出 **20 组一词多写**，其中 12 组是真混用。取占比最高的写法作为统一写法。

| 概念 | 统一写法 | 禁止写法 | 首次出现 |
|---|---|---|---|
| 大语言模型 | **LLM** | 大模型、语言模型、large language model | 大语言模型（LLM） |
| 提示词 | **提示词** | prompt、Prompt、提示语、指令词 | — |
| 系统提示词 | **系统提示词** | 系统提示、system prompt | — |
| 检索增强生成 | **RAG** | 检索增强、retrieval-augmented generation | 检索增强生成（RAG） |
| 模型上下文协议 | **MCP** | Model Context Protocol 全称 | 模型上下文协议（MCP） |
| 词元 | **Token** | token、词元、令牌 | — |
| 嵌入 | **嵌入** | embedding、Embedding | 嵌入（embedding） |
| 推理 | **推理** | reasoning、推断 | — |
| 幻觉 | **幻觉** | Hallucination、臆造 | — |
| 微调 | **微调** | Fine-tuning、精调 | 微调（fine-tuning） |
| 工作流 | **工作流** | workflow、Workflow | — |
| 对齐 | **对齐** | alignment、Alignment | 对齐（alignment） |

#### 三组"看着像混用、其实不是"的，不要合并

| 组 | 为什么会误判 |
|---|---|
| 上下文 / **上下文窗口** | 后者是 context window，指上限，不是同一个东西 |
| 智能体 / **代理** | 「代理」606 次里大半是**网络代理**（proxy），不是 agent。自动统计会误报 |
| 工具调用 / **函数调用** | 在 OpenAI 语境里是两种不同机制，不是新旧叫法 |

> ⚠️ **这条直接影响检查脚本**：术语检查如果只做"同组任一词出现就报错"，上面三组会大量误报。必须先把概念区分开，再检查写法。

#### 规则

- **T1**：同一个概念全篇只用一种写法。
- **T2**：英文缩写已占主导的（LLM、RAG、MCP、Token），沿用缩写；首次出现给中文全称。
- **T3**：中文写法占主导的（提示词、工作流、嵌入、推理、幻觉、微调、对齐），一律用中文。
- **T4**：新增术语先进表，再用。表是唯一权威。

## 3. 句子层

### 3.1 一句一事 `[STE]`

一个句子只表达一个动作或一个判断。

| ❌ | ✅ |
|---|---|
| 把测试电门置于中间位置并松开短路测试电门。 | 1. 把测试电门置于中间位置。<br>2. 松开短路测试电门。 |

**唯一例外**：两个动作同时发生，或后一个动作立即产生结果。

### 3.2 语序 `[STE]`

**条件在前，动作在后。** 条件和动作之间用逗号。

| ❌ | ✅ |
|---|---|
| 把电门置于 NORMAL，当灯亮时。 | 当灯亮时，把电门置于 NORMAL。 |

**时间在前，主体在前。** 「拆卸设备之前」不要写成「在设备的拆卸之前」。

### 3.3 主语与语态 `[中文]`

`[STE]` 要求主动语态。中文的难点不是"被动"，是**没有主语**。

**规则 S1：每句必须有明确主语，或明确的隐含执行者。**

| ❌ 无主语 | ✅ 补主语 |
|---|---|
| 重启服务后即可生效。 | 重启服务。服务重启后生效。 |
| 建议备份后再操作。 | 先备份数据，再执行操作。 |

**规则 S2：能用主动就不用"被"。**

| ❌ | ✅ |
|---|---|
| 配置文件被修改后，服务会被重启。 | 修改配置文件后，重启服务。 |
| 该问题已被修复。 | 已修复该问题。（或写明：谁修复的） |

**规则 S3：只有施动者真的不知道时，才用被动。**
`[STE]` 原文允许：`During transmission, the data was corrupted.`（传输过程中数据损坏，无人为施动者）。

**`[中文]` 注意：脚本会把「由于」「理由」「接受」「感受」里的"由/受"误判为被动。** 这是已知缺陷，见第 8 章。

### 3.4 指代 `[中文]`

**规则 P1：禁止孤立使用"它 / 这 / 那 / 此"。**

| ❌ | ✅ |
|---|---|
| 如果销子与座安装不正确，它们可能损坏。 | 如果销子与座安装不正确，销子可能损坏。 |
| 这个需要确认。 | 这个参数需要确认。 |

判定阈值：**同一段落里，单个代词出现 ≥3 次即违规**（脚本实测值）。

## 4. 段落与结构

**规则 G1 `[STE]`：一段一个主题，主题句放段首。**
读者应当能只读每段第一句就抓住全文骨架。

**规则 G2 `[中文]`：普通段落 ≤3 句；带列表的段落 ≤8 项。**（脚本实测值）

**规则 G3 `[STE]`：能用列表就不用长句。**
列表 = 引导句 + 冒号 + 平行项。每项结构一致（都是动词开头，或都是名词）。

## 5. 标点与格式 `[STE]`

| 规则 | 内容 | 中文处理 |
|---|---|---|
| 禁用分号 | 分号一律拆成两句 | **`；` 一律改成句号** |
| 列表 | 冒号引出，每项大写；整句才加句号 | 中文：每项不加标点，末项加句号 |
| 括号 | 只用于：补充说明、编号、缩写、单复数、替代项 | 不要用括号塞第二层意思 |
| 数字 | 一律阿拉伯数字 | 句首除外 |
| 单位 | 数字与单位紧邻 | `10 MB`，不写 `10MB` 视场景 |

> ⚠️ **你现有脚本把分号当句末**，等于允许分号、还让长句逃过检查。这是必须修的（见第 8 章）。

### 5.1 中文版式（改写自《少数派风格指南》）

表达清楚之后，还有一层"看起来是否专业"。这一层 STE 完全不管，少数派管得很细。取五条最常用的：

| 规则 | ✅ | ❌ |
|---|---|---|
| 汉字与英文/数字之间加半角空格 | 使用 `DeepSeek` 模型 | 使用DeepSeek模型 |
| 中文引用用直角引号 | 「提示词」 | “提示词” |
| 省略号用两个 | …… | 。。。 / ... |
| 中文破折号用两个 | —— | - / — |
| 数字与单位之间加空格 | 10 MB | 10MB |

**效力分级**（借用少数派做法）：本文档未标注的规则一律为**应**（必须）；标注**宜**的为推荐，可不做但要有理由；标注**可以**的为可选。

完整版式规则见 `场景卡-公众号.md` 第 2 节。

## 6. 场景适配

### 6.1 给 AI 的指令（A 档，最严）

```
目标：<一句话，≤20 字>
输入：<文件/目录/范围>
输出：<格式、放哪>
验收：<可判定的标准>
约束：<不许做什么>
```

要点：
- 一句一个要求，不要并列五个"并且"
- 验收标准必须可判定（"文件数 = 51"而不是"整理干净"）
- 不确定就写"不确定"，不要让它猜

### 6.2 写方案（A 档 + B 档混合）

| 章节 | 档位 | 要点 |
|---|---|---|
| 背景 / 目标 | B | 一段一主题，主题句在段首 |
| 现状 / 问题 | B | 用数据和事实，不用形容词 |
| 方案 / 步骤 | **A** | 一步一句，可执行，有输入输出 |
| 风险 / 应对 | A | 条件在前："如果 X，则 Y" |
| 验收 | A | 每条可判定 |

### 6.3 公众号 / 自媒体（C 档，骨架严格 + 表层可读）

> 📄 完整执行细节见 `场景卡-公众号.md`（含版式、标题、开头、配图、发布前检查）。

**保留**：一句一事、术语统一、去套话、结论先行。
**放宽**：句长可到 35 字、允许比喻和节奏、允许口语。
**不放宽**：数据必须有来源；不能为了好读而牺牲准确。

> `[待定]` 这一档最需要你自己的样本校准——STE 是为说明书写的，不是为公众号写的。

## 8. 判定与自检

### 8.1 可自动化检查的（阈值明确）

| 检查项 | 阈值 | 严重度 |
|---|---|---|
| 句长（B 档） | >25 字报警，>30 字错误 | error / warning |
| 句长（A 档） | >15 字报警，>20 字错误 | error / warning |
| 段长 | 普通段 >3 句 | warning |
| 模糊词（强） | 出现 1 次 | warning |
| 模糊词（弱） | 每段 ≥3 个 | info |
| 代词 | 单段单词 ≥3 次 | warning |
| 分号 | 出现即违规 | error |
| 术语 | 与术语表冲突 | warning |

### 8.2 只能人工判的

- 一句话是否真的只说了一件事
- 名词短语的定语是否超过 3 个
- 主语是否明确
- 逻辑关系是否显性
- 数据是否有来源

### 8.3 发布前 30 秒自检

- [ ] 最长那句多少字？超了就拆
- [ ] 有没有"它/这/那"？换成具体名词
- [ ] 有没有"进行/做出/予以"？换成具体动作
- [ ] 有没有"可能/大概/一些"？删掉或给数字
- [ ] 同一个东西有没有换名字？
- [ ] 有没有分号？
- [ ] 每个数字有来源吗？

### 脚本已知缺陷（`ste-checker.py`）

1. 只数汉字，纯英文/数字/代码行长度记 0，永不触发句长检查
2. 表格整块跳过，表格里的长句和模糊词全部漏检
3. **分号被当句末**，等于允许分号，还让长句逃过检查
4. 被动检测用子串匹配，"由于/理由/接受/感受/被动"都会误报
5. 被动、成语、语气助词都是 `info` 级（0 分），**写满被动仍可拿 100 分**
6. 文档说检查"无主语句"，代码里没有实现

## 10. 与 STE100 的取舍

| STE 规则 | 中文怎么办 |
|---|---|
| 受控词典 875 词 | 自建动作词表（本文件 2.1）+ 术语表 |

| 被动语态 | 改为"主语明确 + 少用被字句" |
| 冠词规则 | **放弃**（无对应） |
| 连字符规则 | **放弃** |
| 分号禁令 | **保留**（中文同样适用） |
| 冒号=句号 | **保留**（列表每项独立计数） |
| 段落 ≤6 句 | 收紧到 3 句 |
| 安全说明三级 | 保留：⛔ 危险 / ⚠️ 警告 / 注意 |
