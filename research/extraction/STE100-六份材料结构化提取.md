| # | 反对 | 理由 | 例子 |
|---|---|---|---|

### 2.2 逐字摘录（关键模板）

**（1）80% 基础模板**（L268-282，适用：日常 AI 问答、技术文档、笔记）

```
请用 Simplified Technical English (STE) 风格回答我的问题。

要求：
1. 使用短句，每句不超过 25 个汉字
2. 每段不超过 3 句话
3. 优先使用主动语态
4. 用编号列表展示步骤或要点
5. 避免使用形容词和副词
6. 删除客套话和连接词
7. 每个术语保持一致

我的问题是：
{在此处输入你的问题}
```

**（2）可调浓度模板**（L286-304，适用：同一套提示词覆盖三档场景）

```
请用 STE（简化技术英语）风格回答。

STE 浓度：{100% / 80% / 50%}

浓度说明：
- 100%：严格模式。每句≤15字，全主动语态，无修饰词，纯信息
- 80%：标准模式。大多数句子简短，偶尔使用被动语态，结构清晰
- 50%：轻度模式。关键信息用 STE 风格，解释性内容可适当展开

输出格式要求：
- 使用 Markdown 格式
- 关键步骤用编号列表
- 概念用加粗标注
- 对比用表格

我的问题：
{在此处输入你的问题}
```

**（3）Agent 自检清单**（L1341-1354，适用：任何要"输出即可验收"的 Agent）

```
# STE 自检清单
回答完成后，请逐项检查：
- [ ] 所有句子 ≤ 25 字
- [ ] 所有段落 ≤ 3 句
- [ ] 主动语态占比 ≥ 90%
- [ ] 没有模糊的代词指代
- [ ] 没有套话和冗余修饰
- [ ] 术语使用一致
- [ ] 列表和表格使用得当
- [ ] 信息完整，没有遗漏

```

**（4）自检 5 步法**（L1399-1424，适用：人工或 LLM 复核成稿）

```
## STE 自检流程

步骤 1：句子长度检查
- 统计最长句子的字数
- 如果超过 25 字，拆分它

步骤 2：段落长度检查
- 检查每段的句子数量
- 如果超过 3 句，拆分段落

步骤 3：语态检查
- 统计被动语态句子的比例
- 如果超过 10%，改为主动语态

步骤 4：信息密度检查
- 删除以下内容：
  - 客套话（"非常感谢""希望能帮到你"）
  - 连接词（"然而""因此""综上所述"）
  - 重复信息
  - 无意义的填充语

步骤 5：一致性检查
- 检查同一概念是否用了不同的词
- 统一术语
- 检查代词是否有明确指代
```

### 3.1 逐条

**R1 句子长度**（L240-259）

- 判定：`max_chars = 15 if strict else 25`；`warning_chars = 20 if strict else 30`；逐句调 `count_chinese_chars`。
- `char_count > max_chars` 才报；`sev = "error" if char_count > warning_chars else "warning"`。
- 报什么：`f"句子过长：{char_count} 字（限制 {max_chars}）"`，位置 `段落 {i}·句子 {j}`，snippet 截前 60 字。
- 硬性数值：标准 26-30 字 = warning，>30 字 = error；严格 16-20 字 = warning，>20 字 = error。

**R2 段落长度**（L262-286）

- 判定：`max_sentences_per_para = 3`；`max_with_list = 8`；`has_list_markers = "• " in paragraph`（列表项在 `strip_non_content` L196-197 已被替换成 `"• "`，所以"带列表的段落"放宽到 8 项）。
- 报什么：`f"段落过长：{len(sentences)} 项（限制 {limit} 项）"`，列表段落额外加 ` · 列表段落`。
- 硬性数值：普通段 3，列表段 8。

**R3 hedging**（L289-330）

- 强表：段内每命中一个词报一条 warning，`f"使用了不确定词「{word}」（{count} 次），STE 风格应给出具体信息或注明不确定"`。
- 弱表：先按白名单语境过滤，`weak_count_in_para >= 3` 才报一条 info：`f"弱 hedging 词较多（{weak_count_in_para} 个），建议精简"`。
- 白名单语境：`r"\(推荐"`、`r"（推荐"`、`r"\(建议"`、`r"（建议"`、`r"建议.*术语表"`——在命中词前后 15 字窗口内匹配。
- 硬性数值：弱词阈值 3 个/段；强词 1 个即报。

**R4 习语**（L333-352）

- 判定：`if idiom in paragraph` 子串匹配。
- 报什么：info，`f"使用了习语「{idiom}」，STE 风格应改为直白表达"`。
- 硬性数值：`if len(found) <= 20` 限制 issue 输出 20 条，但 `found` 全量计数（统计值不受限）。

**R5 被动**（L355-388）

- 强标志：每句按 `PASSIVE_MARKERS_STRONG` 顺序找，命中即报 info 并 `break`（每句最多一条）。
- 弱标志：`weak_in_para = sum(paragraph.count(m) for m in PASSIVE_MARKERS_WEAK)`，`>= 4` 时报一条 info。
- 硬性数值：弱被动阈值 4 个/段。

**R6 模糊代词**（L391-409）

- 判定：单个代词在单段内 `count >= 3`。
- 报什么：warning，`f"模糊代词「{pronoun}」出现 {count} 次，建议替换为具体名词"`。
- 硬性数值：阈值 3 次/段/词。

**R7 语气助词**（L412-431）

- 判定：`re.compile(re.escape(particle) + r"[。！？；\s]")`，只认句末助词。
- 报什么：info，`f"句末的语气助词「{particle}」应删除"`；每段每个助词只报 1 次（`break`）。

**R8 术语一致性**（L434-465 + `load_term_table` L478-501）

- 前置：仅 `--terms` 时启用；无术语表直接 `return []`（L436-437）。
- 术语表格式：Markdown 表格行，`line.startswith("|")`，取 `cells[0]` 为标准写法，`cells[1]` 按 `[、/;；,，]` 切分为禁用写法。
- 判定两种：禁用写法与标准写法同现 → `f"术语不一致：同时出现了标准写法「{standard}」和禁用写法「{used}」"`；只出现禁用写法 → `f"建议统一术语：发现「{used}」，标准写法应为「{standard}」"`。

### 3.4 实现层面的真实行为（反推得到，非文档承诺）

1. **只数汉字**：`count_chinese_chars` 仅统计 `\u4e00`-`\u9fff`（L235-237）。纯英文句、代码、数字串的"长度"记为 0，永远不触发 R1。
2. **表格整块不检查**：`strip_non_content` 把 `(?:^[\s]*\|.*\n?)+` 整块替换为 `[表格]`（L187-188），所以表格里的长句、hedging、代词一律漏检。
3. **front-matter 整块删除**（L183），代码块替换为 `[代码块]`（L185），链接只留文字（L192），`**bold**` 去标记（L203）——YAML 元数据和代码里的注释不计入。
4. **分号被当作句末**（L84-85）：`；` 参与切分，等于把一句拆成两句，既不报"禁用分号"，也放宽了 R1 的句长统计。
5. **R5 子串误报**：`"由"` 会命中"由于/理由"，`"受"` 会命中"接受/感受"，`"被"` 会命中"被动"本身。
6. **严重度与官方规则错位**：被动（R5）、习语（R4）、语气助词（R7）全是 info = 0 分，一篇文章写满被动语态仍然可以拿 100 分；能扣分的只有 R1/R2/R3/R6/R8。
7. **docstring 与实现不符**：文件头声称检查"无主语句"（L7-8、L21），但代码里没有任何主语检测，`check_passive` 的 docstring 写"被动语态 / 无主语句检查"（L356）实际只匹配被动标志。实际落地规则就是 R1-R8 八条。

## 五、guide 与 whitepaper 的要点

### 5.1 guide（[asd-ste100-guide.html](reference/ste100/04_应用与解读/asd-ste100-guide.html)）

1. **定位**：ASD-STE100 = 受控自然语言规范；两支柱 = Part 1 写作规则（53 条 / 9 大类）+ Part 2 受控词典（875 批准词 / 1274 禁用替代 / 22 类技术名词 / AmE 拼写）（L802-834、L1155-1176）。
2. **沿革**：1970 年代末 AEA 提出问题 → 1983-06 项目启动 → 1986-02 首版 → 1987 写入 ATA100 成为强制 → 2005 更名 ASD-STE100 → 2025-01 Issue 9（434 页，免费）→ 2026-06 AI 白皮书（L749-785）。
3. **句长二分**：程序类 ≤20 词，描述类 ≤25 词，一句一事（L862-866）；示例把 25 词长句拆成 10+16 词两句（L881-889）。
4. **动词只留 6 种**：不定式 / 祈使 / 一般现在 / 一般过去 / 一般将来 / 过去分词作形容词；禁完成时、进行时、复杂助动词组合（L896-950）。
5. **语态与 -ing**：优先主动，仅描述性文本且 agent 未知时可用被动（L977）；-ing 基本禁用，例外为技术名词、技术名词修饰语、少数批准词（lighting, opening, mating, missing, remaining, during, something）（L1008-1013）。
6. **其他硬规**：禁分号（L1105-1106）、禁缩略形式、禁拉丁缩写、垂直列表、避免代词歧义、保留 `that`、条件在前命令在后、指令用祈使句（L1044-1143）。
7. **Karpathy 与用法**：2026 年 X 帖原话（L1367）+ "80% of the way to ASD-STE100"（L1453）+ 4 个英文 Prompt 模板（L1445-1485）+ 适合/不适合场景（L1493-1503）。
8. **官方立场摘要**：AI 收益 4 条、风险 5 条、"AI 不会取代人类作者，但会重塑技术写作"、组织建议 4 条（L1523-1556）。

### 5.2 whitepaper（[WhitePaper-ASD-STE100_and_AI.pdf](reference/ste100/04_应用与解读/WhitePaper-ASD-STE100_and_AI.pdf)，3 页，STEMG，2026 年 6 月）

1. **目的**：澄清 STEMG 对 AI 用于 STE 内容创作、翻译、技术文档流程的官方立场（p1 Introduction）。
2. **机构边界**：STEMG 只制定和维护标准，"does not engage in producing AI software or tools and does not endorse any of them"（p1）——明确的不背书政策。
3. **标准优先原则**："the standard takes priority, and AI adoption must support, not override, STE requirements"，以保住 clarity、safety、controlled natural language discipline（p1）。
4. **AI 的潜在收益**：效率与生产力、多语文档一致性、STE 合规自动检查（但"currently with varying levels of accuracy"）、术语管理（p1-p2）。
5. **现存挑战**：AI 内容可靠性与事实准确性不稳、术语控制可能被破坏、内容来源可追溯性有限（p2）。
6. **伦理与监管框架**：EU AI Act（风险分级）、UNESCO AI 伦理原则（透明、问责、人类监督）、ISO 与 OECD 建议；对 STE 的含义是合规性与可审计性（p2）。
7. **风险与保障**：透明与可解释、问责归人/组织、数据保密、安全关键场景下的可靠性与排障风险、法律与声誉（需免责声明与使用边界）（p2 Risks and Safeguards）。
8. **行动与建议**：STEMG 已把"不背书政策"扩展到 AI 工具；建议与 AI 开发者保持对话、保密场景优先自研/内部工具、建立 benchmark/评估框架、持续监测法规；使用侧四条 = supportive use only（AI 辅助不替代）、disclaimers（标注范围与限制）、internal policies（数据处理/模型验证/质量保证）、safe and unsafe practices 示例（p3）。结论："AI will not replace human authors, but it is reshaping technical writing"（p3）。

### 6.5 小结（冲突的性质分类）

- **可判定的错误**：C1（1800 vs 875）、C2（Issue 7 vs Issue 9）、C6（分号）——这三条有官方材料可裁，不需要取舍。
- **压平阈值造成的分歧**：C3、C4、C5——官方是"程序句/描述句""agent 是否已知"这种分类式规则，三份中文材料都改成了单一数字，于是各写各的。
- **治理思路不同**：C9、C10、C13——用户手册走"黑名单 + 术语表"，官方走"类别许可 + 受控词典"，脚本走"可选外部术语表"。三者可以并存，但需要先定"谁是主"，否则同一份文档在手册里合规、在脚本里 100 分、在官方标准下不合规。
- **立场级冲突**：C14、C15、C16——官方白皮书是"AI 辅助、人类负责、不背书工具"，AI 手册是"用 STE 提效、推荐工具"，两者不是同一层级的论述，放在一起会互相削弱。
