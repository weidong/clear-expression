# LLM Wiki

用 LLM 构建个人知识库的一种模式。

> 原文：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
> 译文仅供阅读，技术名词保留原文。

这是一份想法文件。它设计成可以直接复制给你的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达高层想法，具体细节由你的 Agent 与你协作完成。

## 核心想法

多数人使用 LLM 处理文档的体验类似 RAG：上传一批文件，LLM 在查询时检索相关片段，再生成答案。这方法可行，但 LLM 每次提问都要从头重新发现知识。知识没有积累。问一个需要综合五份文档的细微问题，LLM 每次都要重新找到并拼合相关片段。什么也没有沉淀。NotebookLM、ChatGPT 文件上传，以及多数 RAG 系统都这样工作。

这里的想法不同。LLM 不只在查询时从原始文档检索，而是**逐步构建并维护一个常驻 Wiki**。这个 Wiki 是结构化的、互链的 Markdown 文件集合，位于你与原始来源之间。加入新来源时，LLM 不只建索引供以后检索。它会阅读来源、提取关键信息，并整合进现有 Wiki：更新实体页、修订主题摘要、记录新数据与旧结论冲突之处、强化或质疑正在形成的综述。知识只编译一次，然后*持续保持最新*，不必每次查询重新推导。

关键区别在这里：**Wiki 是常驻的、会复利增长的成果。** 交叉引用已经存在。矛盾已经被标记。综述已经反映你读过的全部内容。每加入一个来源、每问一个问题，Wiki 都会更丰富。

你几乎不用自己写 Wiki，LLM 负责全部写作与维护。你负责选来源、探索、提出好问题。LLM 承担所有琐碎工作：总结、交叉引用、归档、记账，这些工作让知识库随时间真正有用。实践中，我一边开着 LLM Agent，一边开着 Obsidian。LLM 根据对话修改，我实时浏览结果：跟随链接、查看图谱、阅读更新后的页面。Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

这套模式适用于很多场景。举几个例子：

- **个人**：跟踪自己的目标、健康、心理、自我提升。归档日记、文章、播客笔记，逐步建立对自己的结构化认识。
- **研究**：用数周或数月深入一个主题。阅读论文、文章、报告，逐步构建一个全面 Wiki，并形成不断演进的论点。
- **读书**：边读边归档每一章，为人物、主题、情节线以及它们之间的联系建页。读完时，你拥有一个丰富的伴读 Wiki。可以想想 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝 Wiki：数千个互链页面，覆盖人物、地点、事件、语言，由志愿者社区多年建成。你可以在阅读时个人构建类似的东西，让 LLM 完成所有交叉引用与维护。
- **企业/团队**：由 LLM 维护的内部 Wiki，输入来自 Slack 讨论、会议记录、项目文档、客户通话。也可以让人参与审核更新。Wiki 能保持最新，因为 LLM 承担了团队里没人愿意做的维护。
- **竞品分析、尽职调查、旅行规划、课程笔记、爱好深挖**：任何需要长期积累知识、并希望它有条理而非散落各处的场景。

## 架构

分三层：

**原始来源**：你精选的源文档集合。文章、论文、图片、数据文件。它们不可变：LLM 只读，不改。这是你的事实来源。

**Wiki**：由 LLM 生成的 Markdown 文件目录。摘要、实体页、概念页、对比、总览、综述。这一层完全归 LLM 所有。它建页、在新来源到来时更新页面、维护交叉引用、保持全局一致。你读，LLM 写。

**Schema**：一份文档，例如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md。它告诉 LLM Wiki 如何组织、有哪些约定、摄入来源、回答问题、维护 Wiki 时按什么流程走。这是关键配置文件。它让 LLM 成为守纪律的 Wiki 维护者，而不是通用聊天机器人。随着你摸清自己领域的做法，你和 LLM 共同演进这份文档。

## 操作

**摄入。** 你把新来源放进原始来源集合，让 LLM 处理。一个示例流程：LLM 阅读来源，与你讨论要点，在 Wiki 写摘要页，更新索引，更新 Wiki 中相关的实体页与概念页，最后在日志追加一条记录。一个来源可能触及 10 到 15 个 Wiki 页面。我个人偏好一次摄入一个来源，并全程参与：读摘要、检查更新、引导 LLM 抓重点。你也可以一次批量摄入很多来源，减少监督。适合你的流程由你摸索，并写进 Schema，供以后会话使用。

**查询。** 你向 Wiki 提问。LLM 搜索相关页面、阅读它们，并带引用地综合作答。答案形式可随问题变化：Markdown 页面、对比表、幻灯片（Marp）、图表（matplotlib）、画布。重要的一点：**好答案可以归档回 Wiki，成为新页面。** 你要求的对比、一次分析、你发现的联系，都有价值，不该消失在聊天记录里。这样，你的探索也会像摄入的来源一样，在知识库中复利增长。

**体检。** 定期让 LLM 给 Wiki 做健康检查。检查项包括：页面之间的矛盾、被新来源取代的过时结论、没有入链的孤立页面、被提到却没有独立页面的重要概念、缺失的交叉引用、可以通过网页搜索补上的数据缺口。LLM 擅长提出值得调查的新问题和值得寻找的新来源。这能让 Wiki 在增长中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（也帮助你）在 Wiki 增长时导航。它们用途不同：

**index.md** 面向内容。它是 Wiki 全部内容的目录：每个页面列出链接、一行摘要，可选附日期或来源数等元数据。按类别组织（实体、概念、来源等）。每次摄入后由 LLM 更新。回答查询时，LLM 先读索引找到相关页面，再深入阅读。在中型规模下（约 100 个来源、数百个页面），这方法出奇地好用，也不需要基于嵌入的 RAG 基础设施。

**log.md** 按时间排列。它是只追加的记录，记下发生了什么、何时发生：摄入、查询、体检。一个有用的小技巧：如果每条记录都以固定前缀开头（例如 `## [2026-04-02] ingest | Article Title`），日志就能用简单的 Unix 工具解析。`grep "^## \[" log.md | tail -5` 会给出最近 5 条记录。日志提供 Wiki 演进的时间线，也帮助 LLM 了解最近做过什么。

## 可选：命令行工具

某个阶段，你可能会想建一些小工具，帮助 LLM 更高效地操作 Wiki。最明显的是 Wiki 页面搜索引擎。小规模时索引文件够用，但 Wiki 增长后，你会需要真正的搜索。[qmd](https://github.com/tobi/qmd) 是个好选择：它是面向 Markdown 文件的本地搜索引擎，支持 BM25/向量混合检索与 LLM 重排，全部在设备本地运行。它既有 CLI（LLM 可以通过 shell 调用），也有 MCP 服务器（LLM 可以把它当原生工具）。你也可以自己建更简单的东西。需要时，LLM 可以帮你随手写一个简单搜索脚本。

## 技巧

- **Obsidian Web Clipper** 是浏览器扩展，能把网页文章转成 Markdown。用它快速把来源放进原始来源集合，非常方便。
- **把图片下载到本地。** 在 Obsidian 设置 → 文件与链接中，把「附件文件夹路径」设为固定目录（例如 `raw/assets/`）。然后在设置 → 快捷键中搜索「Download」，找到「Download attachments for current file」，绑定一个快捷键（例如 Ctrl+Shift+D）。剪藏文章后按快捷键，所有图片都会下载到本地磁盘。这一步可选，但有用：LLM 可以直接查看和引用图片，不必依赖可能失效的 URL。注意，LLM 无法一次读取带内联图片的 Markdown。变通办法是让 LLM 先读文字，再单独查看部分或全部引用图片，以获取额外上下文。这有点笨拙，但足够好用。
- **Obsidian 的图谱视图**是观察 Wiki 形状的最佳方式：什么与什么相连，哪些页面是枢纽，哪些是孤岛。
- **Marp** 是基于 Markdown 的幻灯片格式。Obsidian 有对应插件。它适合直接从 Wiki 内容生成演示文稿。
- **Dataview** 是 Obsidian 插件，可对页面 frontmatter 运行查询。如果 LLM 给 Wiki 页面加了 YAML frontmatter（标签、日期、来源数），Dataview 就能生成动态表格与列表。
- Wiki 只是一个 Markdown 文件的 Git 仓库。你免费获得版本历史、分支与协作。

## 为什么有效

维护知识库最烦的部分不是阅读或思考，而是记账。更新交叉引用、保持摘要最新、记录新数据与旧结论的冲突、在几十个页面之间维持一致。人类放弃 Wiki，是因为维护负担增长得比价值快。LLM 不会厌倦，不会忘记更新交叉引用，还能一次改 15 个文件。维护成本接近零，Wiki 就能持续得到维护。

人的工作是筛选来源、引导分析、提出好问题、思考这一切意味着什么。LLM 的工作是其余全部。

这个想法在精神上与 Vannevar Bush 1945 年的 Memex 相关：一个个人的、精选的知识库，文档之间有联想路径。Bush 的愿景比后来的 Web 更接近这里：私密、主动策展，文档之间的连接与文档本身同样有价值。他没能解决的部分是谁来做维护。LLM 接过了这件事。

## 说明

本文有意保持抽象。它描述想法，不描述具体实现。确切的目录结构、Schema 约定、页面格式、工具链，都取决于你的领域、偏好和你选择的 LLM。上面提到的一切都是可选、模块化的：挑有用的，忽略没用的。例如：你的来源可能只有文本，就完全不需要处理图片。你的 Wiki 可能小到只需要索引文件，不需要搜索引擎。你可能不在乎幻灯片，只想要 Markdown 页面。你也可能想要完全不同的输出格式。正确的用法是把它交给你的 LLM Agent，一起实例化一个适合你需求的版本。本文的唯一任务是传达这个模式。其余部分，你的 LLM 能想明白。
