# 个人 LLM Wiki 搭建方案

> 基于 Karpathy 原版 LLM Wiki 模式，适配用户现有 Obsidian + TRAE 工具链的个人知识库搭建方案。
> 方案设计：2026-11-24
> 实际搭建：2026-11-24（同步完成）

---

## 一、设计思路

### 1.1 来源

Karpathy 在 2026 年 4 月发了一份 gist，提出一个核心理念：

> 不要让大模型每次回答问题时都去翻原始资料，而是让它先把资料**编译成一套持续维护的 Wiki**。以后所有回答、查询、综合分析，都直接在这套 Wiki 上进行。

这套思路和普通 RAG（检索增强生成）的本质区别：

| | 普通 RAG | LLM Wiki |
|---|---|---|
| 回答时 | 从原始资料实时搜索、拼装 | 直接读编译好的 Wiki 页面 |
| 知识积累 | 不积累，每次从零开始 | 越用越厚，交叉引用自动生长 |
| 综合回答 | 每次都要跨多篇重新拼 | 综合结论已经在 Wiki 里了 |

### 1.2 用户现状分析

| 维度 | 现状 | 设计影响 |
|---|---|---|
| **Obsidian** | 多个 vault，主用 PARA + CODE + 卡片盒笔记法 | 新建独立 vault 用于 LLM Wiki，不干扰现有笔记 |
| **AI 工具** | TRAE 为主力执行，dsh 为辅 | 规则文件分两层：schema.md（通用，所有工具读）+ AGENTS.md（TRAE 专用） |
| **桌面环境** | Windows 原生 PowerShell 7+ | 脚本和命令优先适配 PowerShell，不用 Git Bash / WSL2 |
| **资料现状** | 已有的 Obsidian 笔记 + 每日持续新增 | 先只处理新资料，存量暂不导入 |
| **安全红线** | 原始资料只读 + 不做全量删除 + 不批量改 | schema.md 写死 `raw/` 不可写，`AGENTS.md` 禁止 LLM 自动裁决矛盾 |
| **工具偏好** | 极简配置，够用即可 | 先不做检查脚本，不装 MCP 插件，纯文件系统方案 |

### 1.3 设计原则

1. **三层分离，权限清晰**：原始层只读、知识层 LLM 写、成品层人写
2. **规则分两层**：schema.md 是宪法，AGENTS.md 是执行手册；换工具不丢规则
3. **成本优先**：Query 永远先读 index.md，不允许全库扫描
4. **只处理新资料**：存量笔记保持原样，避免第一天就把 Wiki 搞乱
5. **检查脚本后置**：少于 50 页时靠规则和人工，过了再上脚本

## 三、三层架构

```
weidong-llm-wiki/           ← Vault 根目录，Obsidian 打开这个文件夹
│
├── raw/                    ← 原始资料层（只读，永远不改）
│   ├── README.md           说明这个目录是只读的
│   └── [用户丢进来的 md/txt/PDF转md/网页剪藏]
│
├── wiki/                   ← 知识编译层（TRAE 写，人读）
│   ├── answers/            综合问答页（type: synthesis）
│   ├── index.md            Wiki 总索引（每次 Ingest 后自动更新）
│   ├── [summary-xxx.md]    一份原始资料的摘要
│   ├── [concept-xxx.md]    某个概念的解释
│   ├── [entity-xxx.md]     某个人/工具/平台的介绍
│   └── [method-xxx.md]     某种方法的步骤、适用条件
│
├── output/                 ← 成品输出层（人写，LLM 协助）
│   └── [YYYY-MM-DD-主题.md]
│
├── 规则文件（所有工具共用 + TRAE 专用）
├── schema.md               通用规则（架构、权限、命名、安全红线）
├── AGENTS.md               TRAE 专用操作指令（三种操作的具体步骤）
│
├── 台账与日志
├── _ingested.md            摄入台账（判断哪些 raw 还没处理的唯一依据）
├── log.md                  时间线日志（每次操作追加一行）
│
└── 版本管理
└── .gitignore              Obsidian/OS/Git/Python 等忽略规则
```

### 三层权限矩阵

| 层 | 路径 | 谁能读 | 谁能写 | 理由 |
|---|---|---|---|---|
| 原始层 | `raw/` | 所有人、所有工具 | **任何人、任何工具都不能写** | 唯一可信的事实来源，一旦被改就无法核对 |
| 知识层 | `wiki/` | 所有人、所有工具 | TRAE 写，人读（人工修正算例外） | 这是 LLM 的编译产物，人负责审核和最终裁决 |
| 成品层 | `output/` | 所有人、所有工具 | 人写，TRAE 协助 | 基于 wiki 内容产出的最终交付物 |

## 四、关键文件说明

### 4.1 schema.md — 通用规则（所有工具共用）

**定位**：整套系统的宪法。不管用 TRAE、dsh、还是手动操作，都要遵守。

**内容结构**：

| 章节 | 作用 |
|---|---|
| 架构总览 | 三层目录 + 权限矩阵 |
| 命名规范 | 文件命名、链接格式 |
| Wiki 页面结构 | YAML frontmatter 格式、正文结构、type 字段取值 |
| 三种核心操作 | Ingest / Query / Lint 的流程描述 |
| 安全红线 | 五条所有人必须遵守的规则 |
| 版本管理 | Git 操作规范 + 三层备份 |
| 和已有体系的关系 | PARA / CODE / 卡片盒 / Agent 四层 / ASD-STE100 的映射 |

**核心设计**：schema.md 不绑定任何特定工具。AGENTS.md 可以重写（比如换模型、换 Agent），但 schema.md 是稳定的——除非架构变了。

### 4.2 AGENTS.md — TRAE 专用操作指令

**定位**：TRAE Agent 打开这个 vault 时自动读取的操作手册。

**内容结构**：

| 章节 | 作用 |
|---|---|
| 身份和目标 | 明确 TRAE 在这个 vault 里的角色是“专职维护者”，不是通用聊天机器人 |
| 目录速记 | 一眼记住每层目录是干什么的 |
| Ingest 操作 | 九步执行顺序 + 提示词模板 |
| Query 操作 | 成本控制流程（先 index 后正文） + 提示词模板 |
| Lint 操作 | 七条检查清单 + 铁律（只报告不修改）+ 提示词模板 |
| 协作方式 | 和用户交互的边界（删改前确认、尊重人工修改） |
| Git 操作 | 什么时候自动 commit、什么时候不推远程 |
| 成本控制 | 什么情况下允许读什么，什么情况下绝对禁止 |

**核心设计**：AGENTS.md 控制在 80 行以内。TRAE 和 Claude Code 都有类似的上下文加载上限建议。规则少而硬，不要模糊的“尽量”、“最好”。

### 4.3 _ingested.md — 摄入台账

**定位**：判断“哪些 raw 文件还没处理”的唯一依据。

**格式**：
```markdown
# 摄入台账

2026-11-24  raw/karpathy-llm-wiki-gist.md  →  wiki/karpathy-llm-wiki-gist.md, wiki/agent-layers.md
2026-11-25  raw/xxx.md                      →  wiki/xxx-summary.md, wiki/concept-yyy.md
```

**为什么台账放在根目录而不是 raw/ 里**：因为 raw/ 是只读的。把台账放根目录，TRAE Agent 可以合法地追加记录而不触碰 raw/ 权限。

### 4.4 log.md — 时间线日志

**定位**：记录每次操作，格式固定前缀便于 grep 查询。

**格式**：`## [YYYY-MM-DD] 操作类型 | 简要说明`

### 4.5 wiki/index.md — Wiki 总索引

**定位**：TRAE Agent 每次 Query 的第一站。不是装饰，是成本控制的核心。

**格式**：`- [[页面名]] - title (updated)`，TRAE 每次 Ingest 后自动重写。

## 五、三种核心操作

### 5.1 Ingest（摄入新资料）

**什么时候触发**：用户把新文件放进 `raw/` 后手动触发

**执行流程（九步，严格顺序）**：
```
1. 读 _ingested.md，对比 raw/，找出 NEW 文件
2. 读 NEW 文件全文
3. 写 summary 页（wiki/xxx.md，type: summary）
4. 检查并更新所有相关的 concept/entity/method 页
5. 新页面互相双链，不许有孤儿页
6. 更新 wiki/index.md
7. 追加到 _ingested.md
8. 追加到 log.md
9. 向用户汇报：新建了哪些、更新了哪些、有什么矛盾
```

**提示词模板**：
```
请执行 Ingest：读取 _ingested.md 对比 raw/，处理所有 NEW 文件。严格按 AGENTS.md 的九步流程执行。完成后汇报新建页、更新页、矛盾标记。
```

### 5.2 Query（查询回答）

**什么时候触发**：用户基于 Wiki 提问时

**执行流程（成本控制优先）**：
```
1. 读 wiki/index.md（这是第一步，不是装饰！）
2. 从 index 找出相关页面
3. 按需打开相关页面（只打开需要的）
4. 综合回答，明确列出用到了哪些 wiki 页
5. 好答案 → 存到 wiki/answers/，标 type: synthesis
6. Wiki 没覆盖 → 如实说没有，用通用知识补的部分明确标注
```

**提示词模板**：
```
请基于 Wiki 回答：<你的问题>。先读 wiki/index.md，找到相关页面后按需打开。回答时列出用到了哪些 wiki 页。好答案存到 wiki/answers/。
```

### 5.3 Lint（定期体检）

**什么时候触发**：每周一次

**七条检查清单（按优先级）**：
```
1. 断链：[[xxx]] 指向的文件不存在
2. 孤儿页：wiki 页没有被任何其他页面链接进来
3. Frontmatter：缺少 title / sources / updated
4. 来源无效：sources 指向的 raw 文件不存在
5. 过期论断：raw 文件改了但 wiki 还在说旧版本
6. 概念重复：两个页面讲同一件事但名字不同
7. 矛盾标注：资料间说法不同但 wiki 里没标出来
```

**铁律**：只报告，不修改。列出问题、位置、建议，等用户逐项确认。

**提示词模板**：
```
请执行 Lint 体检，按 AGENTS.md 七条检查清单的顺序。只报告问题和修改建议，不做任何修改。最后统计：共发现 X 个问题，其中高优先级 Y 个。
```

## 六、Wiki 页面规范

### 6.1 YAML Frontmatter

```yaml
---
title: Agent 四层工程架构
type: concept                        # summary | concept | entity | method | synthesis
sources: [raw/xxx.md, wiki/yyy.md]   # synthesis 页可以引用 wiki 页
updated: 2026-11-24
tags: [AI, Agent, 架构]
---
```

### 6.2 type 字段取值

| 值 | 含义 | 来源 |
|---|---|---|
| `summary` | 一份原始资料的摘要页 | 对应 raw/ 里的某份文件 |
| `concept` | 某个概念的解释页 | 被多份资料共同讨论 |
| `entity` | 某个人/工具/平台的介绍页 | 被多份资料共同讨论 |
| `method` | 某种方法的步骤、适用条件、案例 | 跨资料综合 |
| `synthesis` | 跨 wiki 页的综合问答页 | 对应 wiki/answers/ 下的文件 |

### 6.3 页面正文结构

```markdown
# 一句话简介（30 字以内，让人一眼知道这页讲什么）

## 主体内容
...正文...

## 来源
- [原始资料](../raw/xxx.md) - 第 3 节

## 相关页面
- [[Agent 四层工程 Prompt]]
- [[Agent 四层工程 Context]]
```

### 6.4 命名规则

| 类型 | 格式 | 例子 |
|---|---|---|
| Wiki 页面 | 小写 + 连字符，一页一主题 | `agent-four-layer-architecture.md` |
| 原始资料 | 保持原样（除非明显乱码） | `karpathy-llm-wiki-gist.md` |
| 成品 | `YYYY-MM-DD-主题.md` | `2026-11-24-LLM-Wiki搭建方案.md` |
| **禁止** | `note-12.md`、`Untitled.md`、空格命名 | — |

## 七、安全红线（所有人必须遵守）

| 红线 | 后果 | 违反者 |
|---|---|---|
| **绝不修改 raw/ 下任何文件** | 原始资料是唯一可信来源，改了就无法核对 | 所有人、所有工具 |
| **绝不让 LLM 的通用知识冒充 wiki 内容** | 用户以为是自己收集的观点，其实是模型补的 | 所有 LLM Agent |
| **绝不自行裁决资料间的矛盾** | 并列保留双方说法，标「待裁决」，交用户决定 | 所有 LLM Agent |
| **删除、重命名、改目录结构、改规则文件** | 不可逆或影响面大，必须用户逐项确认 | 所有人、所有工具 |
| **Ingest 台账必须人工审核** | LLM 可能漏记或记错，台账是唯一依据 | 用户 |

## 八、版本管理

### 8.1 Git 规范

整个 vault 是一个 Git 仓库，每次 ingest / query 存答案 / lint 修完后自动提交：

```bash
git add -A
git commit -m "ingest: <原始资料名>"       # 或 query: <问题简述> / lint: <问题数>
```

### 8.2 三层备份

| 层次 | 做什么 | 频率 | 能救什么 |
|---|---|---|---|
| 版本层 | 本地 Git 仓库（每次操作一个提交） | 每次操作 | 改错、删错、想回到上周版本 |
| 异地层 | 推到私有远程仓库（GitHub/Gitee） | 每周 | 硬盘坏、换电脑 |
| 冷备层 | zip 到移动硬盘 | 每月 | 账号被封、远程仓库误删 |

### 8.3 恢复演练（每季度）

1. 远程仓库 `git clone` 到临时目录（别覆盖正在用的）
2. 数 raw/ 文件数，和 _ingested.md 行数对照
3. 随便打开两页 wiki，确认链接没断
4. 演练完删掉临时目录

## 九、使用手册（30 天起步计划）

### 第 1 周：搭起来 + 喂第一份

| 天 | 做什么 |
|---|---|
| Day 1 | Obsidian 打开 vault → 丢一份资料进 raw/ → TRAE 执行 Ingest |
| Day 2~3 | 再加 3~5 份资料，每次一个 Ingest |
| Day 4~5 | 问 2~3 个需要跨多份资料才能回答的问题，好答案存 answers/ |
| Day 6~7 | 跑第一次 Lint，看有没有断链、孤儿页 |

### 第 2 周：喂它

每天加 2~3 份新资料。每天问 1 个问题。

### 第 3 周：连它

看看 Wiki 有没有自然聚成几个主题簇（Obsidian 图谱视图）。试着**基于 Wiki 写出一篇真正的成品**到 output/。

### 第 4 周：体检

跑第二次 Lint，修掉问题。`git add -A && git commit -m “week 4 review”`。

### 退出条件（什么时候说明跑通了）

> 问一个需要用 3 周前存的资料 + 2 天前存的资料综合才能回答的问题，TRAE 能在 30 秒内给出答案，并且你能点回原文核对。

## 十、升级路径

| 当前规模 | 应该加什么 | 判断信号 |
|---|---|---|
| **< 20 页 Wiki** | 只靠 schema.md + AGENTS.md + 人工检查 | 还在熟悉流程 |
| **20~50 页** | Git hook 自动提交（每次 Ingest 后自动 commit） | 人工提交开始觉得烦 |
| **50~100 页** | PowerShell 版简化检查脚本（只做断链 + frontmatter） | 图谱上出现孤儿页、断链 |
| **> 100 页** | qmd 本地搜索引擎（Karpathy 原文推荐） | 纯 index.md 不够用，要靠关键词搜 |
| **> 300 页** | 分层索引（每个领域一个子索引文件） | 主 index.md 太长，一次读不下 |

### 检查脚本（未来版本的设计草案）

等 Wiki 超过 50 页再做，PowerShell 版（Windows 原生，不要 Git Bash/WSL2）：

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `status` | 对比 raw/ 和 _ingested.md，列出 NEW / MISSING | 每次 Ingest 前 |
| `lint` | 断链 + frontmatter + 来源文件检查 | 每周体检 |
| `index` | 扫描 wiki/ 重写 index.md | Ingest 后 |

**和 Karpathy 原文 brain.py 的差异**：
- 去掉了引文逐字校验（需要严格的引文格式，用户现阶段负担不起）
- 去掉了 manifest.json 清单（用 _ingested.md 代替，更简单可读）
- 用 PowerShell 而不是 Python（Windows 原生）

## 十一、已知局限

### 11.1 死区（Karpathy 原文提到）

**50~100 份资料以下，这套 Wiki 的表现跟一个好用的搜索引擎差不多。**

大多数人在这个阶段退出——付了搭建成本，拿回来的还只是搜索。它的价值是**非线性**的，过阈值之后才显现。

### 11.2 坏资料会扩散

一条错的原始资料，会同时污染 10~15 个 Wiki 页面。**所以安全红线里“绝不改 raw/”这条才是最优先的防线**——保证至少还有原始资料可以核对。

### 11.3 没有生命周期机制

没人主动去跑 Lint，Wiki 就会默默腐化。**定时任务不是锦上添花，是必需品**——但用户偏好极简配置，目前先靠手动每周跑一次，等跑通再加自动化。

### 11.4 schema.md 和 AGENTS.md 的边界

两个文件可能会出现规则不一致。**修改其中一个时，必须同步检查另一个**。未来可以考虑写一个简单的一致性检查脚本。

### 11.5 TRAE 的上下文上限

AGENTS.md 控制在 80 行以内是为了适配 TRAE 的加载上限。如果未来 TRAE 升级放宽，可以适当扩充。
