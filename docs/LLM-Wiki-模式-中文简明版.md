# LLM Wiki（简明版）

用 LLM 构建个人知识库的一种模式。

> 原文：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
> 本版为中文译文的简明改写，单句上限 25 字。

这是一份想法文件。
它可以直接复制给你的 LLM Agent。
Agent 例如 OpenAI Codex、Claude Code、OpenCode / Pi。
它的目标是传达高层想法。
你的 Agent 与你协作完成具体细节。

## 核心想法

多数人用 LLM 处理文档，方式类似 RAG。
用户上传一批文件。
LLM 在查询时检索片段，再生成答案。
这方法能工作，但知识没有积累。
每次提问，LLM 都要从头找知识。
问一个细微问题，有时要综合五份文档。
LLM 每次都要重新找片段，再拼起来。
什么也没有沉淀。
NotebookLM、ChatGPT 文件上传，以及多数 RAG 系统都这样。

这里的做法不同。
LLM 不只检索原始文档。
它会逐步构建并维护一个常驻 Wiki。
Wiki 是结构化、互链的 Markdown 文件集合。
它位于用户与原始来源之间。
加入新来源时，LLM 不只建索引。
它会阅读来源，提取关键信息。
然后，它把信息整合进现有 Wiki。
整合包括更新实体页、修订主题摘要。
它还会记录新旧结论的冲突。
它强化或质疑正在形成的综述。
知识只编译一次，然后持续更新。
每次查询不必重新推导。

关键区别在这里。
Wiki 是常驻的、会复利增长的成果。
交叉引用已经存在。
Wiki 已经标记了矛盾。
综述已经反映读过的全部内容。
每加入一个来源，Wiki 就更丰富。
每问一个问题，Wiki 也更丰富。

你几乎不用自己写 Wiki。
LLM 负责全部写作与维护。
你负责选来源、探索、提出好问题。
LLM 承担琐碎工作。
这些工作包括总结、交叉引用、归档、记账。
它们让知识库随时间真正有用。
实践中，我一边开着 LLM Agent，一边开着 Obsidian。
LLM 按对话修改。
我实时浏览结果。
我跟随链接、查看图谱、阅读更新后的页面。
Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

这套模式适用于很多场景。
例如：

- **个人**：跟踪目标、健康、心理与自我改进。
  归档日记、文章、播客笔记。
  逐步建立对自己的结构化认识。
- **研究**：用数周或数月深入一个主题。
  阅读论文、文章与资料。
  逐步构建全面 Wiki，形成演进的论点。
- **读书**：边读边归档每一章。
  为人物、主题、情节线建页。
  也为它们之间的联系建页。
  读完时，你会有一个丰富的伴读 Wiki。
  可参考 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page)。
  它有数千个互链页面。
  页面覆盖人物、地点、事件与语言。
  志愿者社区多年建成。
  你也可以在阅读时建一个类似的 Wiki。
  LLM 完成交叉引用与维护。
- **企业/团队**：LLM 维护内部 Wiki。
  输入来自 Slack 讨论、会议记录、项目文档、客户通话。
  也可以让人审核更新。
  Wiki 能保持最新。
  因为 LLM 做了团队没人愿做的维护。
- **竞品分析、尽职调查、旅行规划、课程笔记、爱好深挖**：
  这些场景都需要长期积累知识。
  你也希望知识有条理，而不是散落各处。

## 架构

分三层。

**原始来源**：你精选的源文档集合。
包括文章、论文、图片、数据文件。
这些文件不可变。
LLM 只读，不改。
这是你的事实来源。

**Wiki**：LLM 生成的 Markdown 文件目录。
包括摘要、实体页、概念页、对比、总览、综述。
这一层完全归 LLM 所有。
它建页，也在新来源到来时更新页面。
它维护交叉引用，保持全局一致。
你读，LLM 写。

**Schema**：一份配置文档。
例如 Claude Code 的 CLAUDE.md。
或者 Codex 的 AGENTS.md。
它告诉 LLM Wiki 如何组织。
它也说明有哪些约定。
它规定摄入、回答、维护的流程。
这是关键配置文件。
它让 LLM 成为守纪律的 Wiki 维护者。
而不是通用聊天机器人。
随着你摸清领域做法，你和 LLM 共同演进这份文档。

## 操作

**摄入。**
你把新来源放进原始来源集合。
然后让 LLM 处理。
示例流程如下。
LLM 阅读来源，与你讨论要点。
它在 Wiki 写摘要页。
它更新索引。
它更新相关的实体页与概念页。
最后，它在日志追加一条记录。
一个来源通常会触及 10 到 15 个 Wiki 页面。
我个人偏好一次摄入一个来源。
我会全程参与。
我读摘要、检查更新、引导 LLM 抓重点。
你也可以批量摄入很多来源。
这样可以减少监督。
适合你的流程，需要你自己摸索。
摸清后，写进 Schema，供以后会话使用。

**查询。**
你向 Wiki 提问。
LLM 搜索相关页面，阅读它们。
然后，它带引用地综合作答。
答案形式随问题变化。
可以是 Markdown 页面、对比表、幻灯片（Marp）。
也可以是图表（matplotlib）或画布。
重要的一点：好答案可以归档回 Wiki。
归档后，它成为新页面。
你要求的对比、一次分析、你找到的联系，都有价值。
它们不该消失在聊天记录里。
这样，你的探索也会复利增长。
它和摄入的来源一样，都会沉淀进知识库。

**体检。**
定期让 LLM 给 Wiki 做健康检查。
检查项包括页面之间的矛盾。
也包括新来源已取代的过时结论。
也包括没有入链的孤立页面。
也包括提到却没有独立页面的概念。
也包括缺失的交叉引用。
也包括可用网页搜索补上的数据缺口。
LLM 擅长提出值得调查的新问题。
它也擅长指出值得寻找的新来源。
这能让 Wiki 在增长中保持健康。

## 索引与日志

两个特殊文件帮助 LLM 与你导航。
它们用途不同。

**index.md** 面向内容。
它是 Wiki 全部内容的目录。
每个页面列出链接与一行摘要。
还可附日期或来源数等元数据。
目录按类别组织，例如实体、概念、来源。
每次摄入后，LLM 更新索引。
回答查询时，LLM 先读索引。
它找到相关页面，再深入阅读。
在中型规模下，这方法很好用。
规模在 100 个来源、数百个页面左右。
它不需要基于嵌入的 RAG 基础设施。

**log.md** 按时间排列。
它是只追加的记录。
它记下发生了什么、何时发生。
记录包括摄入、查询、体检。
一个有用的小技巧：
每条记录用固定前缀开头。
例如 `## [2026-04-02] ingest | Article Title`。
这样，日志就能用简单 Unix 工具解析。
`grep "^## \[" log.md | tail -5` 会给出最近 5 条。
日志提供 Wiki 演进的时间线。
它也帮助 LLM 了解最近做过什么。

## 可选：命令行工具

某个阶段，你可以建一些小工具。
它们帮助 LLM 更高效地操作 Wiki。
最明显的是 Wiki 页面搜索引擎。
小规模时，索引文件够用。
Wiki 增长后，你会需要真正的搜索。
[qmd](https://github.com/tobi/qmd) 是个好选择。
它是面向 Markdown 文件的本地搜索引擎。
它支持 BM25/向量混合检索与 LLM 重排。
全部计算都在设备本地运行。
它既有 CLI，也有 MCP 服务器。
LLM 可以通过 shell 调用 CLI。
它也可以把 MCP 服务器当原生工具。
你也可以自己建更简单的东西。
需要时，LLM 可以帮你写一个简单搜索脚本。

## 技巧

- **Obsidian Web Clipper** 是浏览器扩展。
  它能把网页文章转成 Markdown。
  用它可快速把来源放进原始来源集合。
- **把图片下载到本地。**
  在 Obsidian 设置 → 文件与链接中，设置附件文件夹路径。
  把它设为固定目录，例如 `raw/assets/`。
  然后在设置 → 快捷键中搜索「Download」。
  找到「Download attachments for current file」。
  为它绑定快捷键，例如 Ctrl+Shift+D。
  剪藏文章后，按下快捷键。
  所有图片都会下载到本地磁盘。
  这一步可选，但有用。
  LLM 可以直接查看和引用图片。
  它不必依赖容易失效的 URL。
  注意，LLM 无法一次读取带内联图片的 Markdown。
  变通办法是先让 LLM 读文字。
  再让它单独查看部分或全部引用图片。
  这样能获得额外上下文。
  这有点笨拙，但足够好用。
- **Obsidian 的图谱视图**最适合观察 Wiki 形状。
  你能看到什么与什么相连。
  也能看到哪些页面是枢纽，哪些是孤岛。
- **Marp** 是基于 Markdown 的幻灯片格式。
  Obsidian 有对应插件。
  它适合直接从 Wiki 内容生成演示文稿。
- **Dataview** 是 Obsidian 插件。
  它可以对页面 frontmatter 运行查询。
  LLM 可以给 Wiki 页面加 YAML frontmatter。
  frontmatter 包括标签、日期、来源数。
  这样，Dataview 就能生成动态表格与列表。
- Wiki 只是一个 Markdown 文件的 Git 仓库。
  你免费获得版本历史、分支与协作。

## 为什么有效

维护知识库最烦的部分不是阅读或思考。
最烦的是记账。
记账包括更新交叉引用、保持摘要最新。
也包括记录新旧结论的冲突。
也包括在几十个页面之间维持一致。
人类放弃 Wiki，是因为维护负担增长太快。
负担增长得比价值快。
LLM 不会厌倦。
它不会忘记更新交叉引用。
它还能一次改 15 个文件。
维护成本接近零，Wiki 就能持续得到维护。

人的工作是筛选来源、引导分析。
人还要提出好问题，思考这一切意味着什么。
LLM 的工作是其余全部。

这个想法与 Vannevar Bush 1945 年的 Memex 相关。
两者在精神上相通。
Memex 是一个个人的、精选的知识库。
文档之间有联想路径。
Bush 的愿景比后来的 Web 更接近这里。
它是私密的、主动策展的。
文档之间的连接与文档本身同样有价值。
他没能解决的部分是谁来做维护。
LLM 接过了这件事。

## 说明

本文有意保持抽象。
它描述想法，不描述具体实现。
目录结构、Schema 规范、页面格式与工具链。
这些都要看你的情况。
它们取决于你的领域、偏好和选择的 LLM。
上面提到的一切都是可选、模块化的。
挑有用的，忽略没用的。
例如，来源只有文本时，你不需要处理图片。
如果你的 Wiki 很小，只需要索引文件。
这样，你不需要搜索引擎。
你也可以不在乎幻灯片，只想要 Markdown 页面。
你也可以选择完全不同的输出格式。
正确的用法是把它交给你的 LLM Agent。
你和 Agent 一起实例化一个适合你的版本。
本文的唯一任务是传达这个模式。
其余部分，你的 LLM 能想明白。
