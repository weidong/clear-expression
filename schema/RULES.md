# 简明表达规范

> 写作规则（知识库版本）。
> 本文件是 LLM 维护 Wiki 时的“写作宪法”。
> 每次写入或修改 Wiki 页面之前，必须先阅读本文件。
> 基于 ASD-STE100 Issue 9 精简改编，适配个人知识库场景。
> 本规范不限语种。中文写作适用，中英混排同样适用。

---

## 一、总则

1. **清晰优先**：写作的第一目标是清晰，其次是简洁，最后才是优美。
2. **读者优先**：假设读者对该主题了解不多。避免假设读者知道你知道的东西。
3. **一词一义**：一个术语只能有一个含义。如果同一个概念有多种说法，统一为标准术语（见 DICT.md）。

---

## 二、句子规则

### 规则 1：使用短句
- 每句只表达一个意思。
- 理想句子长度：10-20 个汉字或 8-15 个英文单词。
- 最长不超过 30 个汉字或 25 个英文单词。
- ❌ 错误：检索增强生成是一种将信息检索与文本生成相结合的技术，它先从文档库中找到相关内容然后把这些内容和问题一起提供给语言模型以帮助模型生成更准确的答案。
- ✓ 正确：检索增强生成是一种技术。它将信息检索与文本生成相结合。系统先从文档库中检索相关内容，再将这些内容提供给语言模型。

### 规则 2：使用主动语态
- 明确指出谁做什么。
- 避免“被”“由……所”等被动表达。
- ❌ 错误：相关文档将被检索系统找到。
- ✓ 正确：检索系统找到相关文档。

### 规则 3：使用具体名词，避免模糊指代
- 少用“它”“这”“其”“该”等代词。
- 如果代词可能引起歧义，就重复名词。
- ❌ 错误：模型读取文档后，它将其与问题结合并生成答案，这提高了准确率。
- ✓ 正确：模型读取文档后，将文档内容与问题相结合，然后生成答案。这种方法提高了答案的准确率。

### 规则 4：避免复合句
- 不要把多个意思塞进一个句子。
- 把长句拆成短句。
- 使用编号或项目符号来组织相关的句子。

---

## 三、词汇规则

### 规则 5：使用常用词
- 优先使用简单、常见的词汇。
- 不要使用生僻词或“高级词汇”来显得专业。
- ❌ 错误：该系统可藉由向量嵌入的方式来语义化检索相关文档。
- ✓ 正确：该系统使用向量嵌入来搜索语义相关的文档。

### 规则 6：一词一义
- 每个概念只有一个标准名称。
- 所有同义表达统一为标准术语。
- 标准术语列表见 DICT.md。
- 例如：统一使用“大语言模型（LLM）”，不用“大模型”“大型语言模型”“语言大模型”等变体。

### 规则 7：术语首次出现必须定义
- 每个专业术语在页面中首次出现时，必须给出清晰定义。
- 定义格式：`[术语]：[定义]`。
- 例如：向量嵌入：将文本转换为数学向量的过程。向量可以表示文本的语义含义。

### 规则 8：避免修辞手法
- 不要使用比喻、夸张、拟人等文学手法。
- 不要使用“相当于”“类似于”之类的类比作为主要解释方式。
- 知识是工具，不是散文。
- ❌ 错误：向量数据库是 RAG 的心脏。
- ✓ 正确：向量数据库是 RAG 系统的核心组件。它存储文档的向量表示。

---

## 四、结构规则

### 规则 9：用编号列表写步骤
- 有先后顺序的操作用编号列表（1. 2. 3.）。
- 每个编号项描述一个完整动作。
- 以动词开头。

### 规则 10：用项目符号写特性
- 并列的特性、组成部分、分类用项目符号（-）。
- 每个项目符号项描述一个独立条目。

### 规则 11：页面结构标准化
- 每个页面必须包含以下部分（按顺序）：
  1. 元数据（frontmatter 格式的键值对）
  2. 定义 / 描述（页面的第一句话说清楚“这是什么”）
  3. 详细内容（按小节组织）
  4. 相关链接
  5. 来源

### 规则 12：使用描述性标题
- 标题要准确描述页面内容。
- 不要使用花哨或模糊的标题。
- 概念页直接用概念名做标题。
- 操作指南页以“如何……”开头。

---

## 五、信息质量规则

### 规则 13：每条事实都有来源
- 所有事实陈述都要标注来源编号。
- 来源编号格式：`[来源编号]`，放在句子末尾。
- 来源列表在页面底部。
- 例如：使用 RAG 后，答案准确率从 60% 提升到 82% [论文1]。

### 规则 14：区分事实和观点
- 客观事实直接陈述，并标注来源。
- 主观判断或推测必须明确标记。
- 使用“研究表明”“作者认为”“据推测”等词语区分。

### 规则 15：保持中立客观
- 不要使用带有感情色彩的词汇。
- 不要做价值判断，除非是引用他人的评价。
- ❌ 错误：这个方法非常棒，完美解决了问题。
- ✓ 正确：该方法将准确率提升了 22 个百分点 [论文1]。

## 六、特殊格式规则

### 规则 16：数字和单位
- 数字使用阿拉伯数字。
- 单位使用标准符号。
- 数字和单位之间加一个空格。
- 例如：`512 MB`、`3.5 小时`、`100 篇文章`

### 规则 17：链接格式
- 内部 Wiki 链接使用 `[[页面名称]]` 格式。
- 外部链接使用 `[显示文字](URL)` 格式。
- 链接文字要描述链接目标，不要用“点击这里”。

### 规则 18：代码和技术术语
- 代码、命令、文件名使用反引号包裹。
- 技术缩写首次出现时给出全称。
- 例如：`检索增强生成（Retrieval-Augmented Generation，简称 RAG）`

## 七、适用范围与灵活度

- **严格执行**：概念页、实体页、操作指南页（这些是“参考资料”，必须精确）
- **适度放宽**：对比页、综合分析页（可以有更多论述，但仍保持清晰）
- **灵活掌握**：个人笔记、思考记录（作为 raw/ 下的原始素材，不要求符合简明表达规范）

**不适用**（一律保持原样，不改写、不简化、不翻译）：

- 代码、代码注释、commit message。
- 标识符：变量名、函数名、字段名、类名。
- API 名、接口路径、命令、参数、配置键名、文件名与目录路径。
- 原样引用的日志、报错信息、命令输出：引用时一字不改。
- 他人原文的引文：保留原措辞。需要改写时另起一段，不与引文混写。

> 为什么：改这些内容会让程序失效，或让引用失真。本规范管给人读的说明文字，不管机器读的字面量。

> 💡 提示：如果你不确定某条规则是否适用，优先遵守。清晰永远不会错。

## 八、补充规则（2026-11-24 真实验证后新增）

### 规则 19：只改真被动
- 只把“被 + 动词”的结构改为主动语态。
- 以下用法不是被动，不要改：
  - 名词性用法：被审对象、被调查人、被告。
  - 定语从句：被 Agent 坑过的人。
- ❌ 错误改写：把"被审对象"改成"审对象"。
- ✓ 正确：审校结果由 dsh 生成 → 审校结果来自 dsh。

### 规则 20：表格单元格也要短
- 每个单元格不超过 20 字。
- 单元格内禁止长定语和多重并列。
- 一格只放一个判断。需要解释时，把说明移到表格下方的正文。
- ❌ 错误：`| 部分有效：不可动清单、容量红线、副本与 SHA-256、30 天隔离、删除门槛继续有效；旧目录映射不执行 |`
- ✓ 正确：单元格只写`部分有效`，具体保留项写在表格下方。

### 规则 21：拆句后必须补衔接
- 长句拆开后，句与句之间要有连接词，否则读起来是断的。
- 并列关系用：同时、另外。
- 因果关系用：因此、原因是。
- 转折关系用：但、不过。
- 顺序关系用：先、再、最后。
- 禁止连续三个以上没有连接词的短句。

### 规则 22：句长按文体分档
- 操作步骤（怎么做）：单句不超过 20 字。
- 说明性内容（是什么、为什么、方案）：单句不超过 25 字。
- 公众号与科普文章：单句不超过 37 字。
- 超过对应档位时，优先拆句，不要删信息。

### 规则 23：使用中文标点
- 中文正文使用全角标点。
- 引号用“”，不使用英文直引号。
- 英文单词内部的标点保持半角。
- ❌ 错误：他说 "AI 已经改变一切"
- ✓ 正确：他说“AI 已经改变一切”

### 规则 24：控制破折号密度
- 破折号只用于补充说明。
- 同一段落内不超过 1 处。
- 全篇参考值：每千字不超过 3 处。
- 替代写法有两个：用冒号引出解释，或用句号另起一句。
- ❌ 错误：他来了——带着方案——但没有预算
- ✓ 正确：他来了，带着方案。但他没有预算。

## 九、汇报类规则（2026-11-25 新增）

> 适用对象：向人汇报“做了什么、结论是什么、还需要人定什么”的说明文字。
> 页面正文仍按第一到六节写。这一节管交付说明，不管知识内容。

### 规则 25：结论先行
- 第一句写这次回复最关键的信息。
- 首句内容按类型确定：
  - 进度说明：写当前动作与对象。
  - 结果汇报：写状态与完成范围。
  - 排查结论：写原因，或写“原因未确认”。
  - 请求决定：写待决事项。
  - 多项总结：写总体结论或总结范围。
- 细节、证据、过程放在首句之后。
- ❌ 错误：我先读了三份文档，又对比了口径，发现有冲突……
- ✓ 正确：三份文档有 10 处口径冲突。明细见下文。

### 规则 26：状态词固定
- 写工作状态时，只用下表 10 个词，不临时造词。
- 状态词必须带范围。写“已完成：登录刷新逻辑的代码修改”，不写“已修改登录刷新逻辑”。
- 不得用“已 + 任意动词”代替状态词。
- 工作状态与验证状态分开写，互不替代。

| 状态词 | 含义 |
|---|---|
| 已完成 | 范围内的工作全部做完 |
| 部分完成 | 只做完范围的一部分 |
| 未开始 | 还没有开始 |
| 进行中 | 正在做，尚未完成 |
| 已验证 | 结果经过检查，方法可复现 |
| 未验证 | 结果没有经过检查 |
| 失败 | 检查执行了，但没有通过 |
| 跳过 | 明确决定不做 |
| 阻塞 | 依赖未满足，无法继续 |
| 未确认 | 缺少证据，当前无法判断 |

### 规则 27：每个结论写明验证状态与方法
- 对效果、行为、检查结果的结论，写清四件事：状态、方法、结果、覆盖范围。
- 状态取自规则 26 的词表。
- 没做的检查写“未验证”，不写“应该没问题”。
- 做了但没过的检查写“失败”，附关键失败输出。
- 缺证据无法判断写“未确认”，并写清怎么确认。
- 只读过资料就下的结论写“未验证：仅依据文档内容”，不得冒充运行验证。
- ❌ 错误：改好了，应该没问题。
- ✓ 正确：已验证：在本机运行 `npm test`，12 项全部通过，覆盖登录与刷新两个模块。

### 规则 28：请人决定时列编号选项
- 需要人拍板时，列编号选项，不用开放式提问。
- 每个选项写一个动作和它的后果。
- 推荐项放第一，标“（推荐）”。
- 选项必须互斥。不互斥就拆成两轮问。
- ✓ 正确：
  1. 先改规则，再改工具（推荐）：规则先落地，工具随后跟上。
  2. 只改规则：改动小，但工具会漏报新规则。

### 规则 29：不叙述过程
- 不写“我先……然后……接着……”。
- 直接写读者需要的关键信息与证据。
- 过程只保留能复现结论的部分：命令、路径、版本。
- ❌ 错误：我先看了文件，又跑了一遍脚本，最后发现……
- ✓ 正确：原因：`lint.py` 第 42 行漏判分号。复现命令：`python lint.py a.md`。

### 规则 30：证据可定位
- 引用代码写 `路径:行号`。
- 引用提交写提交号。
- 引用命令写完整命令。
- 引用文档写文档路径加章节名。
- 证据要能让读者自己找到同一处内容。
- ❌ 错误：代码里有问题。
- ✓ 正确：`schema/RULES.md:201-207` 规定了破折号密度上限。
